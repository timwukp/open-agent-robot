# 測試設計 — open-agent-robot

本檔是這個 repo 的測試契約:每一項功能對應具名測試、指定方法、可否證的通過標準,
以及一個**必須被殺掉的突變體**。它跟代碼同一個 PR 落地,因為一份沒有跟代碼一起改的
測試設計會在第二次重構之後變成考古資料。

閱讀順序:先讀 §0(為什麼這樣分級),再跳到你要動的那個子系統。

## 0. 第一原理:一個測試的價值等於它的 oracle

測試的強度上限由它拿什麼當「正確答案」決定。不同 oracle 能支撐的結論差好幾個等級,
混用會讓「全綠」變成一句沒有內容的話。所以先分級:

| 級別 | oracle | 能證明什麼 | 例 |
|---|---|---|---|
| **D** 確定性 | 純函式的精確期望值 | **正確性**(可當 CI 閘) | 切分邊界索引、封閉謂詞拒絕、級聯刪除 |
| **R** 回放 | 凍結的人工標註 fixture | **不退化**(門檻是回歸線,不是真理) | 30 條查詢 top-5、邊界 F1 |
| **M** 量測 | 沒有真值,只有預算 | **符不符合預算** | p50/p95 延遲、USD/回合 |
| **A** 對抗 | 單邊 | **有洞**(永遠不能證明沒洞) | 紅隊集、注入、路徑穿越 |
| **H** 人工 | 人的判斷 | 體驗與法遵的可觀察面 | 揭露聽得到、遊戲好不好玩 |

由此推出六條規則。每一條都是為了擋一個具體的、已經發生過的失效模式:

### 規則 1 — 不用 LLM 當測試判官
判官當獎勵訊號時,pass rate 從 0.72 升到 0.94,而真實正確率平在 **0.20**(三個 seed);
嚴格三判官集成仍然接受 **55%** 的錯誤答案。唯一有效的緩解(commit-first,
false positive 0.719 → 0.012)需要「單一可提交答案」,對開放對話不適用。

→ 任何需要語義判斷的性質,**要嘛降維成機器可檢查的代理量,要嘛移出 CI 進人工 UAT**。
永不當閘。T-D5(「你確定嗎」抗壓)之所以只用**算術/日期/場景計數**這種機器可判的題目,
就是這條規則的直接後果。

### 規則 2 — 每個斷言配一個具名突變體
突變體產生**位元相同**的輸出,代表我測錯了量,不代表我很安全。
每一輪突變測試必須包含一個**無突變對照**,而且它必須綠——否則是 harness 壞了在報成功。

實作上還要更嚴一級:突變體「被殺掉」不等於「被該殺它的那個檢查殺掉」。
`tests/test_deploy_path.py` 的 `MUTANTS` 表因此是 `名稱 → (突變, 預期的 finding 字串)`,
只有 exit code 非零而預期訊息沒出現的話,測試仍然紅。

### 規則 3 — 對抗測試只能證明有洞
紅隊的通過標準寫成「**凍結集 0 逃脫**」並明文標註**這是下限不是保證**;
集合只增不減;新發現的逃脫先進集合,再修代碼。

### 規則 4 — 量測不是正確性
只對照預算,不對照真值。**n < 20 的 p95 等於 max**(現存唯一的 Guardrails 數字就是
別人 client-side 的 n=15)。**逾時單獨計數,永不算成錯誤**——botocore 60 秒預設值曾把
4 個未完成的呼叫算成 4 個錯答案,等於憑空扣掉 8 分。

### 規則 5 — 失敗不中止,但空掃必須非零退出
逐案輸出標記後匯總,一個案子紅不能讓後面的案子不跑。
反過來,**掃到 0 個檔案、收集到 0 個案例、解析出 0 個節點,必須非零退出**:
「什麼都沒檢查」和「檢查了而且都過」在輸出上長得一樣,除非你讓它們不一樣。

已實作的三個地方:`check_deploy.sh` 的 `die`(exit 3)、`conftest.py` 的逐模組收集下限、
`fixture_manifest.read_manifest` 對格式錯誤拋 `ManifestError` 而不是回傳空列表。

### 規則 6 — 數字由 harness 輸出,文件引用 harness
手打進散文的數字等於未驗證。本檔所有數字都標了量測日期與環境;
會隨代碼變動的數字(檢查數、測試數、秒數)寫在 `pytest.ini` 的 marker 說明裡,
跟 harness 同一個檔案,而不是散在文件各處。

這條規則自己也需要一個閘,因為我違反過它:**T-J8**(`infra/doc_counts.py`)把本檔 §0 表格
與兩份 README 引用的每一個案例數,對帳回 `pytest --collect-only` 的輸出。
「記得更新 README」不是流程,是一個會失敗的假設。

## 1. 可測試性 = 設計約束

這是為什麼 S0(測試骨架)排在所有功能之前:下面每一條違反了,對應的測試不是變難寫,
而是**不會被跑**。而不會被跑的測試等於不存在。

| 約束 | 為什麼 | 違反的後果 |
|---|---|---|
| 純模組零 ROS import(`store`/`segment`/`recall`/`consolidate`/`opponent`/`guard`) | 在筆電上跑 pytest,不需要 EC2 | 測試只能在 GPU 機上跑 → 不會被跑 |
| **時鐘可注入**(模組內不直接呼叫 `time.monotonic()`) | 45 s 靜音、5 min 上限、15 s 冷卻、衰減、**以及延遲量測 harness 自己** | 一個測試要跑 45 秒 → 會被標 slow → 被 skip → 被刪;而在量測 harness 上是更糟的後果:**讀到錯的數字而且只在特定負載下紅**(見下方) |
| **Bedrock client 可注入,且替身要會說謊** | 證明 L0 不經 LLM、證明守衛擋得住 | 回聲替身讓分支永遠走不到,斷言拿測試自己餵的值跟自己比 |
| **儲存路徑可注入** | 測試不得污染 `$HOME/oar-data/` | 測試互相污染,第二次跑才紅 |
| 隨機源可注入(seed) | 猜拳、取樣 | 不可重現的紅 = 被當成雜訊忽略 |

「替身要會說謊」這一條不是偏好,是有證據的。`tests/test_doubles.py` 裡有一組並列證明:
同一個有 bug 的函式、同一個斷言、兩種替身、相反的結論——
`test_echo_double_lets_the_bug_pass` 通過(bug 存活),
`test_lying_double_catches_the_bug` 抓到。這對測試就是這條約束的證據本身。

**時鐘那一條也是有證據的,而證據是我自己違反它。** `safety/guardrail_latency_harness.py` 原本直接呼叫
`time.monotonic()`,而 `tests/test_guardrail_latency.py` 的語言差異突變體測試用一個**真的 `time.sleep()`**
的替身製造 10/25/40 ms 三組延遲,再斷言 `between_group_p50_spread_ms == approx(30, abs=15)`。
它單獨跑綠、在自己檔案裡跑綠,在**整套離線測試一起跑**的時候讀到 **46.0 ms**——超出容忍上界 45。
(這一段原本手打了套件總案例數,而 `infra/doc_counts.py` 立刻報 findings:那個數字的句型
跟突變體總數的句型撞在一起,變成同一個模式出現兩次。T-J8 抓到的第一個真實缺陷是我自己的散文。)
`pytest.ini` 沒有裝任何隨機化插件,收集順序是確定的,所以這不是順序污染,是**機器負載**:
一個跨在兩個 sleep 級距上的中位數會不均勻地吃進排程器的 overshoot。

這裡的修法是根因而不是清潔工:**不是把容忍放寬到 abs=25**,而是把 `now` 注入
`apply_seconds` / `measure` / `measure_runs`(生產路徑的預設值仍是真的 `time.monotonic`),
替身改成 `advance()` 一個 `FakeClock`。斷言隨之從 `approx(30, abs=15)` 變成 **`== 30.0`**——
時鐘一被注入,那個排程表**就是**量測值,近似的餘地本來就不該存在。
一個量測 harness 的測試不可以去量它自己跑在哪台機器上;放寬容忍只會把下一次的紅推到下一台更忙的機器。

`tests/doubles.py` 提供:
- `FakeClock` — `monotonic()`/`time()`/`advance()`/`sleep()`,sleep 記錄而不阻塞
- `LyingBedrockClient` — 回覆與 prompt 無任何共同子串,且**內含三個絕不可信的東西**:
  白名單外的 gesture 標籤、注入的 `SYSTEM:` 指令、關於身分的斷言
- `ExplodingBedrockClient` — 用 `__getattr__` 而不是兩個具名方法:只擋 `converse` 的替身
  在有人改用 `converse_stream` 的那天就停止擋了,而測試會因為錯誤的理由變綠
- `FakeRosNode`/`FakePublisher`/`FakeLogger` — 只覆蓋節點真正用到的 rclpy 面;
  用不到的一律 `AttributeError`,因為需要更多 rclpy 的節點,是邏輯該被抽成純模組的節點
- `seeded_rng(seed)`

3. **「每行等寬」不是不變量。** 我原本用行寬集合當交錯的偵測器,實測 `[8371..8376]` 六種寬度都出現:

4. **拒絕的記錄不得消耗序號**(缺陷 B,`append` 重排):序號在 `json.dumps` 之前就取走時,

   代價是多一次 `json.dumps`。**缺陷 A** 是 `_publish(最後一筆)` 而非 `_publish(高水位)`:
   `append` 在鎖內取號、鎖外入列,所以 6 可以比 5 先入列;T-A7 就是為它寫的。
5. **T-A5 照字面寫會是一條測不到自己聲稱的東西的測試。** 設計表說「對種子檔案卡呼叫任何寫入 API」,
   照字面實作就是測 `memory/profile.py`;但寫入 API 是 `Store.write_snapshot(name, obj)`,

   `pytest.raises(StoreError)` 對兩者都綠,判別必須打在精確型別上。
6. **這一輪的鎖讓 `tests/test_store.py` 的四個既有快照測試變紅,而那個紅是對的。** 它們用

   「任何覺得鎖礙事的人都能把它掀開」的測試,而且原子性測試會變成在測鎖而不是在測換名。

**T-B1、T-B2、T-B4 這一輪(S4)落地**(`memory/segment.py`,59 個案例,17 個進 L3),
落地時有三件事跟設計表寫的不一樣,而三件都是「設計表自己的通過標準太弱」:

1. **T-B2 的通過標準「邊界仍產生」殺不掉它自己指定的突變體。** 純事件驅動的切分器在
   「後來有人又說話了」的流上會產生**完全相同**的邊界:同一個索引、同一個 reason、同一份
   hash。`tests/test_segment.py` 直接把這件事寫成一條斷言(兩個模組的 digest 相等),
   所以差別不在**哪裡**切,在**什麼時候**知道要切。真正的判別是:流已經結束、後面再也
   沒有任何事件,episode 仍然關閉。這件事有後果而不只是漂亮:關閉 episode 才會觸發 S5 的
   摘要與嵌入,事件驅動版本會把一整晚的鞏固延後到下一次有人說話的那一刻。
2. **T-B4 的通過標準對 `set` 迭代序無效。** 「同輸入跑兩次比 hash」是在**同一個行程**裡跑
   的,而 `set` 的迭代序在一個行程的生命週期內是固定的。`set(self.rules)` 突變體因此在
   本機完全可重現、在下一台機器上錯——正是 T-B4 要防的那件事,而 T-B4 寫下的方法看不到。
   殺它需要兩個 `PYTHONHASHSEED` 不同的子行程,**而且**需要一個同時命中兩條規則、且這兩條
   規則的相對順序在那兩個 seed 下不同的事件(`activity` 與 `scene`,實測而非假設)。反過來
   `sorted(self.rules)` 跨行程穩定,要用另一種事件(同時命中 `silence` 與 `activity`)才殺得掉。
   一個突變體、一條斷言的對應關係在這裡是假的,所以寫成三條。
3. **硬上限是不變量,所以跨距上限必須是「不含等號、且在 append 之前」關閉。** 事件每 40 s
   一次可以完全不觸發 45 s 靜音規則;落在第 320 s 的那一個,如果照 turn 上限的寫法
   (append 之後、`>=` 關閉),會產生一個跨距 **320 s** 的 episode——存在目的是把跨距壓在
   300 s 以下的規則,變成它被超過的原因。turn 上限可以含等號,因為 20 turns 滿足「不超過
   20」;跨距不行,因為那個值是事件帶進來的,不是這個模組加出來的。兩者的不對稱不是風格,
   `cap_findings()` 對突變體回報 320.0s,對真模組回報空清單。

另外三件不在設計表裡、但屬於同一類「拒絕而不是預設」的決定:
未知的 `kind` **拒絕**而不是「不貢獻任何東西」——後者是 turn 上限在事件照樣流動的情況下
悄悄消失的路徑(突變體:25 個拼錯 kind 的事件產生一個 0 turns 的 episode,沒有任何上限
觸發);`ts` 逆行**拒絕**,而 `_close()` 故意不重設 `_last_ts`,因為由 `tick` 觸發的邊界之後
沒有任何東西再寫入那個值,那個時刻是唯一擋得住「時間倒退」的地方;`Episode` 關閉後不可變,
因為 `cap_findings()` 讀的正是可以被事後改掉的那幾個欄位。
`rules=` 是一個**可審查的參數**而不是註解(理由與 `Store._allow_ephemeral` 相同:T-B1 的
5×5 恆等式沒有別的做法),配一條掃描證明 `tests/` 以外沒有人傳它,以及一條種一行進去的正控。

(「A guarantee enforced in the reader is a comment; enforced in the one writer, it holds for
code that has never heard of the profile module」)。

**普查真正讀到多少,是量出來的,而且比它看起來的少。** 磁碟上三個呼叫點,只有一個傳的是 AST
讀得懂的 dict 字面值:`er.delete` 把 tombstone 建在區域變數裡再 append(所以參數是 Name),
而 `agent/context.py` 根本沒有呼叫點——它只是**造**出 payload,由呼叫者轉交。這個弱點寫成資料
(`OPAQUE_SITES` / `BUILDER_ONLY` / `NOT_PRODUCERS`),每一筆都要具名替它覆蓋的那個測試,而那個測試
必須真的存在。理由跟 §0 規則 5 一樣:一個略過不透明呼叫點的普查,報出來的「乾淨」跟「每個呼叫點都沒問題」
是同一個輸出。第四個不透明的呼叫點會在這張表上紅,不會安靜地不被檢查。

**它讓另一個測試付出了代價,而代價寫下來才算誠實。** `tests/test_store.py` 的 key-sorting 那一案
原本刻意用 `{"zebra": 1, "alpha": 2}`,**正因為** `audit` 當時沒有 schema,它那句字面值只做一個宣稱;
現在同一句字面值同時斷言了 `AUDIT_FIELDS["profile_loaded"]`。T-A1 的代價更大也更值得看:
它需要 > 8 KB 的紀錄來逼出部分寫入,而 8300 字元的 audit 字串**已經不是生產環境到得了的狀態**了,
所以 audit 那一半換成 tombstone 的 `removed` 清單(2000 個序號,11008 bytes)——那才是這條串流
合法地大的形狀,壓力一點沒少,而且來自系統真的會產生的紀錄。

**兩個誠實邊界。** 一、上限檢查的是紀錄自己的**頂層字串**,不遞迴進 list/dict;今天每個容器型欄位
裝的都是機器產生的內容(`removed` 是序號、`blocks` 是區塊名),而 tombstone 的 `removed` 本來就該大,
所以一刀切的遞迴大小上限會拒絕一份正確的刪除收據——走訪容器是另一個帶自己突變體的改動。
二、任何對字串**值**的檢查都分不出「我們寫的散文」與「別人說的散文」;那是 provenance 不是 content,
而 provenance 只能靠走訪呼叫點來查。

T-C4 的 fixture **必須保證兩個分支都存在**(只剩 E 的事實、有第二來源的事實),
並用計數斷言證明,否則測試會空綠。

**T-C4 的刪除動作在 S5 的刪除半段落地**(`memory/erase.py`,`tests/test_erase.py` 50 個案例),
落地時有七件事跟設計表寫的不一樣,而其中第一件把通過標準本身改掉了:

1. **「五條路徑各 0 命中」不能實作成 `deletion_findings == []` —— 那個標準在真實的 store 上不可達。**
   我第一版就是這樣寫的,紅了才發現原因不在刪除路徑:一筆**沒有 episode 的猜拳回合**是真實系統的
   合法狀態。Track B 的 `game_node` 是 fire-and-forget 把每局結果送給 `memory_node`,所以在沒有
   episode 開著的時候打的那局,永久地沒有歸屬。`deletion_findings` 會把它報成 `ORPHAN`,而那是對的
   —— 孤兒是偽造級聯刪除最便宜的方法 —— 但**刪除前就存在的孤兒不是關於這次刪除的證據**。
   要求列表為空,只有把「沒有歸屬的回合」從 fixture 裡拿掉才能滿足,也就是把 `_plan_rps` 存在的理由
   刪掉。所以通過標準拆成三條獨立的宣稱:①**沒有命中指名 E** ②**沒有路徑沒跑到** ③**每條路徑的
   孤兒數沒有變多**。第三條才是原措辭真正想抓的缺陷(刪 episode 條目、留著事件)。
   同一個修正也套在**收據**上:一次**正確**的刪除,它的 `findings` 不是空的,因為有一樣東西是
   故意不刪的,而說出來就是整個設計。

2. **tombstone 在移除之前寫,不是之後。** 兩種崩潰不對稱:寫完 tombstone 就斷電 → 稽核日誌宣稱了一件
   磁碟還沒做的事,`tombstone_findings` 會報出來,而**同一筆交易重跑就補完**;反過來先移除再斷電 →
   檔案少了記錄而沒有任何東西說明原因,跟毀損無法區分,沒有任何後續執行救得回來。

3. **`audit` 串流不可被刪除路徑縮短**(`store.REWRITABLE = {"events": True, "audit": False}`)。
   一份刪除路徑改得動的稽核日誌不是稽核日誌:「發生過一次刪除」這筆記錄會被下一次刪除移走。
   代價寫出來而不是藏起來:**沒有任何東西強制稽核記錄不引用使用者原文**,所以每張收據都帶
   `RETAINED`,而 tombstone 的欄位集合是封閉的(`episode/kind/removed/seq/ts/why`,沒有 `text`),
   並且由**讀取端**驗證 —— 只有寫入端檢查的話,保護的是今天這個寫入端;以後有人為了讓收據更好讀
   而加一個 `excerpt`,不會經過本模組的建構函式。

4. **歸屬檔(`episodes.json`)最後刪,而 `sorted()` 恰好是最錯的順序**(它排第一)。
   這一條的代價我一開始寫錯了:我斷言突變體造成的損害「連不變量也看不到」,實測是**看得到** ——
   tombstone 帶著序號,所以 `tombstone_findings` 精確指出 `events.jsonl` 還留著 seq [1,2,3]。
   真正的代價比「不可偵測」窄,而且仍然是真的:**`delete` 修不了它**,因為 `delete` 是從歸屬檔造計畫的,
   重跑會找到 0 筆事件而報成功;修復需要一個人去讀 tombstone。正確順序 → 重跑就補完;
   突變體順序 → 一條稽核 finding 加一次人工修復。

5. **刪除登錄冊由磁碟導出,不由 `recall.PATHS` 導出。** 上一輪的 `coverage_findings` 已經把
   `audit.jsonl` 報成「檢索未覆蓋」,而它從來不會出現在任何路徑的 `reads` 裡 —— 一份由 `PATHS`
   導出的登錄冊會讓稽核串流永遠不被分類,而「沒人決定」跟「決定保留」在檔案上長得一樣。
   兩個函式對同一個檔案給出不同答案,正是這個設計的重點。

6. **卡片的兩個分支被兩種不同的機制殺掉,所以兩個突變體都必須存在。**
   `if remaining:` → `if False:`(永遠整條刪)寫得出一份合法的卡片,只有「另一個 episode 的事實還在」
   這條斷言會紅;→ `if True:`(永遠不整條刪)**連寫都寫不出來**,因為 `profile.py` 規定只有 `seed`
   可以沒有來源,一條 `observed` 而 `source_episode_ids` 變空的事實會被它自己的讀取端拒絕,
   而寫入前的重新解析把那個拒絕變成一次 `EraseError`。只留一個突變體會有一種機制沒被測到。

7. **保留期只測機制,不測門檻。** `RETENTION_DAYS = 90` 是政策預設值:沒有量測、沒有法規指名,
   所以對 90 斷言就是對一個猜測斷言。被斷言的是機制 —— 邊界在一秒解析度下**兩側各差一秒都精確**、
   時鐘可注入(否則這是一個要等九十天的測試,也就是不會被跑的測試)、以及**沒有 `end_ts` 的
   episode 被報出來而不是被靜靜留下或靜靜掃掉**(它永遠不會過期,所以它落在每一個保留期之外)。

落地這一輪還修掉一個**既有缺陷**:`Store.__init__` 的 `self._seq = 0` 從不從磁碟恢復。
在 `rewrite_stream` 之前這只是難看,之後它是跨 episode 的資料遺失 —— 刪除是**按序號**指名記錄的,
而 `consolidate.episode_id(seq)` 又用序號導出 episode 身分,所以計數器從 0 重啟之後,「刪掉 seq 5」
會指到兩個不同 episode 的兩筆記錄。修法是 `store.recovered_seq(root)`(兩個串流共用一個計數器,
所以要掃兩個檔案),而修的時候我自己造了第二個缺陷:只恢復 `_seq` 而讓 `_durable` 留在 0,
`flush()` 的預設目標是 `self._seq`,於是打開一個非空的 store 再關掉會**掛住**五秒然後留下等待中的執行緒
—— 兩個變數持有同一個事實,只更新其中一個。回歸測試是
`test_opening_a_populated_store_and_flushing_nothing_returns`。

**T-C6 這一輪(S3.5)落地**(`memory/salience.py`,69 個案例),落地時有一件事跟設計表寫的不一樣:

1. **設計表指定的那條斷言測不到它聲稱的東西 —— 它會被「從來沒讀過」滿足。**
   「開關關閉時餵各種聲學輸入 → 值位元相同」對兩種系統都綠:一個正確忽略韻律的系統,
   以及一個**因為任何原因**從來沒讀到那些欄位的系統 —— 本檔裡拼錯的欄位名、真實節點不會送的
   訊息形狀、一組所有值都塌成同一個數字的網格。三者都讓測試綠而什麼都沒證明。
   所以**開關開啟那一半不是加分,是正控**:同一個網格必須讓分數動起來,那才確立了
   「本來有東西可以被忽略」。網格的鍵來自 `salience.ACOUSTIC_FIELDS` 而不是本檔,
   所以改名也不能把它悄悄清空;另有一條斷言要求每個欄位在網格裡**真的變動過**。
   這條也決定了 `prosody_term` 的形狀:**它拒絕範圍外的值而不是 clamp**。一個 clamp 版本
   餵真實的 Hz 會對每一個輸入都回 1.0 —— 一個**讀得到輸入卻恆定**的項,而正控會在
   「這一項其實是活的」的情況下失敗。拒絕讓失敗可歸因:單位錯就是單位錯,不是項死了。
   同理「缺測量」拋錯而不是當 0.0:**沒有測量不是測到零**,把「沒有音高資料」記成
   「講得很平」是從一個缺席裡做出的、關於某人怎麼說話的推論。

第二件事不是修正而是新增的契約,記在 §2.A 的 **T-A9**:S3.5 的價值不在於公式難改,
而在於**值是持久的**。`events.jsonl` 裡的一個 salience 只跟同一個公式產出的另一個可比,
而 S6 改權重時如果沒人記下是哪個公式產的,「這兩筆不一致」與「這兩筆不是同一個量」
就永遠分不開 —— 而且不可回溯地分不開,因為那個資訊從來沒被寫下來。所以
`store.RECORD_FIELD_DEPS` 在 `append` 就拒絕一筆只有分數沒有 id 的記錄,那是**最後一個
還能修的時刻**;store 用資料宣告**配對**,`memory/salience.py` 擁有 **id 本身**
(兩份 id 就是配對律要防的那個缺陷,所以有一條唯一創造者斷言,附一個正控 ——
一個找不到被植入的第二份的掃描器,不構成「只有一份」的證據)。

**T-C5 的結構半段已提前實作**(在 `safety/guard.py`,跟 §D 同一個 PR),
而寫的過程推翻了上面那格的通過標準 —— 見 §D 修正 4:「指令區與基線位元相同」
這個 oracle **會被它要抓的缺陷滿足**,所以真正落地的是一個創造不變量的拒絕,
不是一個觀察。注入型的召回內容這一輪落地(`agent/context.py` + `tests/test_context.py`,
見 §C 修正 8–13),而它殺掉的那個突變體走的是 **base prompt** 那一邊 ——
憲法那一邊被 `instruction_region` 的拒絕擋掉,base prompt 那一邊沒有柵欄標記所以進得去,
擊殺它的是指令區對**分開組出來的**無記憶基線的位元相同。

**T-C1 的 goal 半段這一輪(S4.5)落地**(`memory/store.py` 的 `GOALS` / `WHY_REQUIRED` /
`check_why`,`tests/test_why.py` 77 個案例,凍結集 `tests/fixtures/why_goal_rejects.jsonl`)。
編號接續上面的修正 1(那條屬於 T-C6):

2. **計劃書自己寫下的枚舉記法描述的是一個開集。** 計劃 §S4.5 把家族寫成
   `user_requested_*` / `game_*` / `vision_event` / `scheduled_*`,而 `*` 不是一個封閉集合。
   照字面實作成前綴測試,`user_requested_ignore_stop_words` 會被接受,
   於是這個欄位**恰好變成它被加進來要堵的那個洞** —— 自由文字以後綴的形式回來。
   所以落地的是**成員測試**,家族只是文件上的分組:`GOALS` 是 11 個寫出來的成員,
   而凍結集有 6 條 `family_prefix` 專門釘這件事。
   一般化的形狀是:**前綴對掃描器是對的,對閘是錯的**。掃描器的失效模式是
   「沒注意到新名字」(見 `feedback_scope_as_namelist`),所以要用前綴 + 天花板;
   閘的失效模式是「多接受了一個」,所以只能用寫出來的成員。同一個記法,
   相反的方向,因為失敗落在另一邊。
   這條也決定了「無前綴測試」這個宣稱**用什麼證**:`memory/store.py` 本身有一個合法的
   `startswith`(`write_snapshot` 檢查檔名),所以檔案級的 grep 會需要一張豁免表,
   而一張能被教會一個例外的表也能被悄悄教會第二個。落地的斷言因此走 `check_why` 的
   **AST**,範圍剛好是那個閘。
3. **正規化突變體殺不掉「它會不會拋錯」,只殺得掉「寫下去的東西還讀不讀得回來」。**
   `.lower()` 與 `.strip()` 兩個突變體仍然拒絕全部 4 條 instruction 列 —— 一個只斷言
   「拒絕集 0 條被接受」的測試對它們是綠的。它們破壞的是 T-C1 的另一半職責:
   `why.goal` **同時是檢索鍵**,而正規化版本落盤的是呼叫端的拼法,
   於是那筆記錄躺在檔案裡、卻查不到自己的 goal —— 一個桶被拆成兩種拼法。
   所以這兩個突變體的擊殺是**行為式**的:用真實的 `filter_by_goal` 去讀突變體寫下的檔案,
   真實讀取端**拒絕讀**。同理三條查詢側斷言:未知 goal 的查詢**必須拋錯而不是回 `[]`**
   (打錯字、改名、過期的呼叫端否則都讀成「本來就沒有這種紀錄」,而那正是保留期清掃
   會據以行動的讀法,見規則 5 的同一族),普查**必須含 0**
   (否則「沒有紀錄帶這個 goal」與「這個 goal 已經不在集合裡」輸出一樣)。
   還有一條時序斷言:因為內容被拒而失敗**不能消耗序號** —— 一個缺號跟一次刪除
   長得一樣,而那正是稽核日誌存在要消除的唯一歧義。

兩件不算修正但值得寫下的判斷。第一,**一個欄位只有一次是免費強制的:在第一個寫入者存在之前。**
讀 goal 的是 S5,所以直覺的順序是「等到有人消費它再加」。但今天 `memory_node` 只往 `audit` 追加,
於是在 `events` 上強制一個理由**動到零個生產代碼呼叫點**,只動十幾行測試;S5 之後再加同一條要求
就變成一次針對**無法重新導出的個資檔案**的遷移,而那個時刻的壓力是「為舊紀錄把欄位改成選填」——
也就是這個邊界從來不存在的那個版本。計劃把 S4.5 排在這裡,可量測的部分是:放這裡成本為零,
放下一階段成本無界。第二,**豁免的串流不豁免枚舉**:`audit` 不必帶 `why`,
但帶了就一樣驗證 —— 一個在豁免串流上不被檢查的宣稱,正是這套詞彙取得第一個額外成員的地方。
`WHY_REQUIRED` 因此把 `STREAMS` 的每一個成員都寫出來(不用 `.get(stream, False)`),
並有一條斷言要求兩邊的鍵集合相等:**沒有人做的決定跟「決定豁免它」在輸出上分不開。**

**T-C2 與 T-C3 這一輪(S5 離線半段)落地**(`memory/consolidate.py`,
`tests/test_consolidate.py` 62 個案例,L3 選到 12 個)。編號接續:

4. **T-C3 的兩條通過標準都會被一個錯的身分方案滿足 —— 而且是綠著錯的。**
   設計表要的是「`source_episode_ids` 非空,且每個 id 都解析得到」。一個由
   **位置**導出 episode id 的方案永遠滿足這兩條:刪掉前面一個 episode 之後,
   後面每一個的位置往下移一格,於是一條原本來源是第 7 個 episode 的事實
   **成功解析到第 6 個**。沒有東西缺,沒有東西拋錯,而這條事實悄悄取得了一個
   從來沒有產生過它的來源。由**首筆記錄的 store 序號**導出則相反:同一次刪除留下一個
   解析不到的懸空 id —— 級聯刪除找得到、也動得了。兩個方案在刪除之後都是錯的,
   只有一個是**可偵測地**錯,而可偵測就是刪除路徑(T-C4)的全部要求。
   `segment.Episode` 同時帶著 `seqs` 與 `indices`,所以這不是一個假想的選項,是一個
   兩行之差的選項;能看出差別的測試只有一個形狀:**刪掉再重新切分**。
   §S4.5 已經買下另外一半 —— 因內容被拒的記錄不消耗序號 —— 所以這裡鑄出來的 id
   沒有任何一個缺號會被誤讀成一次刪除。
   id 因此**定寬補零**(`ep-000042`):`source_episode_ids` 是排序後存的,而混寬方案會把
   `ep-1000000` 排在 `ep-999999` 前面,同樣的來源集合就有兩種序列化。序號超出寬度
   **拒絕而不加寬** —— 加寬是那種「只在第一百萬筆事件、在生產環境、在沒人會重讀的檔案裡
   出現一次」的缺陷。
5. **「N ≥ 2」的計數對象是**場合**,不是提及次數,而這條規則的擊殺只有一個形狀。**
   按 mention 計數的突變體在「提及次數與場合數一致」的輸入上跟真實模組**輸出相同**,
   而那是大部分輸入。分開它們的只有一個形狀:同一個值在同一個 episode 裡出現兩次 ——
   也正好是一個「每句話產一條候選」的抽取器會意外產生的形狀。所以這個突變體不是被
   「事實變少了」殺掉的,是被那一條 fixture 殺掉的,而 fixture 本身有一條斷言證明它
   **真的是**那個形狀(`len({o["episode"] for o in same}) == 1`),不是假設。
   規則的理由也不是防說謊:它防的是**聽錯**、假設語氣(「如果我討厭芫茜的話」)、
   以及轉述別人的話。一個場合就是一次機會,而區分「持久的偏好」與「轉錄假影」最便宜的
   東西就是它會不會在**另一個場合**回來。計劃 §0-6 明說封閉謂詞集擋得住捏造的**事實**、
   擋不住**偏好**,所以這條計數律就是那道門的守衛,不能被悄悄放寬。
6. **值的比對是逐位元的,而這是一個決定,不是一個限制。**
   同一個偏好的兩種拼法在這裡算兩條候選,各自需要自己的兩個 episode。
   替代方案 —— 在計數器上游放一個模糊比對器 —— 是一個能把 `allergy: 花生` 與
   `allergy: 花生醬` 合起來的元件,而一次錯誤的合併不只是存錯值:它**製造出**
   N ≥ 2 所要求的第二個場合。**一個閘,如果它的證據可以由它所要守的東西合成出來,
   就不是閘。**所以任何合併都是抽取器明示且留痕的決定,這個模組只數它被交到手上的東西。
   同一條理由讓未 strip 的值被**拒絕**而不是被 strip:`Fact` 在建構時會 strip,
   所以一個對原始字串分組的閘會把 `"芫茜"` 與 `"芫茜 "` 數成兩個場合、再存下同一列 ——
   **分組鍵必須就是落盤的那串位元**,否則這個計數關於的是檔案裡沒有的東西。
   這是 §S4.5 的「拒絕而不正規化」用在另一個理由上:那裡的風險是一個檢索桶被拆成兩種拼法,
   這裡是兩個計數塌成一列。
7. **trust 是證據的種類,不是它的數量。** `confirmed` 要求本人說過「是」
   (`user_confirmed` 通道),而**永遠不會**由重複次數得到,不管幾個 episode 同意。
   按次數升級意味著同一個聽錯重複夠多次就變成已確認的事實 —— 那正是 N ≥ 2 被選來防的
   結果;多出來的 episode 是同一種證據的更多份,不是更好的一種。`seed` 在這裡從不鑄造:
   那個等級對 `source_episode_ids` 的豁免只為一份手寫檔案存在。
   `INFERENCE_ALLOWED` 把 `PREDICATES` 全部 18 個成員寫出來(理由與 `WHY_REQUIRED` 相同),
   有一條斷言要求鍵集合相等,還有一條要求它**不是全 False** —— 一張全 False 的表會讓這條
   規則空轉、也讓 `inference_not_allowed` 成為唯一到得了的判定。
   一次鞏固的報告也含**全部**判定的 0 值:只報寫進去了什麼的一夜,會讓
   「沒人提案」與「全部被拒」變成同一句話,而第二種才是該被叫醒的那一種。

**T-C5 的注入半段這一輪落地**(`agent/context.py`,`tests/test_context.py` 43 個案例),
而落地的第一步不是測試,是把接縫接上去 —— 編號接續上面:

8. **這條測試沒東西可注入,因為那個接縫從來沒有被部署。** 對 `safety/guard.py`
   十四個公開名字做 AST 普查、比對全部生產檔案的結果是:**十三個在測試之外沒有任何呼叫者**,
   其中包含 `load_constitution`、`instruction_region`、`data_region`、`compose_system` 本身;
   唯一有呼叫者的是 `stop_requested`(來自 `game/game_node.py`)。而 `agent/agent_node.py`
   **根本沒有 import `safety.guard`**,它的系統提示是 `SYSTEM + loader.l1_index(self.skills)`
   ——一個 725 字元的模組級字面值加技能索引,憲法不在裡面,指令/資料的接縫也不在裡面。
   所以 S2 那一輪成立的是「`compose_system` 這個函式是對的」,不是「機器人的提示是對的」;
   T-C5 的通過標準講的是**被送出去的那個 prompt**,於是接線必須排在任何注入斷言之前。
   一般化的形狀是:**一個沒有呼叫者的邊界不是邊界,而全綠的測試套件不會提到這件事** ——
   會提到的是一次由生產檔案導出的呼叫者普查。
9. **柵欄名字會撞,而修正屬於生產者。** `guard.data_region` 把每個名字算成
   `re.sub(r"\W", "", name)[:32]`,所以 `card` 與 `c-a-r-d`、任何兩個前 32 個 word 字元相同的
   名字、以及 `""` / `"!!!"` / `"data"` 全部塌成同一個柵欄名 —— 兩個區塊一個名字,
   讀者無法說出任一個在哪裡結束,而那正是柵欄唯一提供的東西。可以只在消費端用一個封閉
   `BLOCKS` 元組避開,但那只讓**這一個**呼叫者安全;所以 `data_region` 現在**拒絕**碰撞
   (不變量在生產者被創造,不是在消費者被觀察),`agent/context.BLOCKS` 是另一半。
10. **第一版的一個突變體產生位元相同的輸出,而那代表我測錯了量。** 召回區塊原本有一個
   `hit.path != CARD_PATH` 的過濾,翻掉它什麼都不會變 —— 因為卡片區塊先建、共用的 `seen`
   集合已經把那些文字擋掉了。§0 規則 2 的形狀在這裡是可操作的:**輸出位元相同的突變體
   要改的是斷言,不是加一句「這樣很安全」**。落地的設計因此把卡片區塊當成先建的
   **聯集**、刪掉那個多餘的過濾,擊殺點移到卡片迴圈的 `==`。
11. **「常駐卡片優先」會靜默丟掉記憶。** 想那個突變體的時候才看清楚:常駐卡片由
   `memory_node` 經 `transient_local` 送來,卡片路徑讀的是磁碟上的 `profile.json`,
   兩邊在**正常運作下**就會不一致(最後一次發佈之後寫進去的事實只存在於一邊)。
   取任一邊都會讓一條事實從 prompt 裡消失,而且沒有任何地方說有東西被扣住了。
   所以卡片區塊是**聯集**:常駐在前、去重、順序穩定。
12. **findings 回傳給稽核,不寫進 prompt。** 一個降級的回合必須對日誌可見,而不是對模型
   描述:跟模型說「語義路徑不可用」是花 token 教它我們的管線,還邀請它去談論這件事。
   這也是 T-F3 那條「降級成只用檔案卡並說出來」在**唯一能執行它的那一層**的樣子。
13. **字面值天花板是煙霧偵測器,不是鎖。** `PROMPT_LITERAL_CEILING = 120` 抓得到被貼回節點的
   725 字元提示,抓不到用五段 40 字元拼回來的規則(中文子句遠低於天花板)。誠實的邊界是:
   真正的鎖是 `system_text` 的**唯一寫者**斷言 —— 不管節點自己串了什麼,只有組裝器的回傳值
   到得了 Converse 呼叫。天花板配一條 `len(BASE_PROMPT) > 120` 的非空泛斷言,
   否則把它設成一百萬也會綠。

落地時有五件事跟設計表寫的不一樣,**一件是設計表的通過標準本身錯了**(修正 4):

1. **T-D1 的通過標準被實作方式取代了,而取代它的東西更強。**
   設計表要「參數化:狀態集合從 `game_node` 原始碼推導 × 冷卻中/外」。
   狀態集合**仍然是推導的**(`tests/test_game_wiring.py::node_states`,今天導出四個:
   `idle`/`inviting`/`await_chant`/`chanting`),但它已經不是承載這條性質的東西 ——
   `STOP_WORDS` 從 `game/game_node.py` 收到 `safety.guard.stop_requested`,
   而那個函式**唯一的參數是文字**。一個看不到狀態的函式不可能在某個狀態表現不同,
   所以「每一個狀態都生效」變成**簽名的性質**,對今天的四個狀態成立,對明年有人加的第五個
   也成立;逐狀態參數化只會是同一條斷言抄四遍。
   測試改成驗兩件更小更利的事:節點在**讀 `self.state` 之前**就派給反射
   (兩個語句位置的整數比較,不是看起來像),以及 `STOP_WORDS` 在全樹**只有一個創造者**。
   附帶效果是 T-D2 的執行期半段也不再需要 rclpy:把 `boto3` 換成一個**碰到就拋**的物件
   再呼叫反射,而靜態 import 掃描代替不了這件事(函式內的 lazy `import boto3` 它看不到)。
   還沒做的只剩**節點層**的執行期半段(真的建一個 `GameNode` 配會拋錯的 Bedrock 替身),
   那個要 rclpy,留在 L5。
   **一個刻意的不對稱**:`stop_requested("不要停")` 回 `True`,而 `forget_request("不要忘記…")`
   回 `None`。刪除路徑防否定是因為誤判會**毀掉資料**;停止路徑不防,是因為這台機器人真正
   出過的事故是**反方向**的(LLM 連環開局而「停」被忽略)。誤停的代價是一局被打斷。
   這條不對稱**寫成一個測試**而不是一句註解,所以未來想「順手加上否定處理」的改動
   必須先刪掉那個測試 —— 也就是必須把話說出口。
2. **憲法需要一條它自己的測試,設計表漏了。** 條文檔案是**執行期資料**,不是說明文件:
   刪掉一條不是文件問題,是「機器人少了一條邊界而沒有人會發現」。
   所以 `REQUIRED_CLAUSES` 是一份手寫普查,而它**只能是斷言,不能是運算元** ——
   兩邊互相比對,任一方向不等都紅。「文字而已」在該寫的地方寫下來
   (C3/C8/C10 只有文字,C2/C5/C7 有結構在後面),因為把一句求模型客氣的話
   跟一個封閉集合強制的邊界混為一談,就是提示被誤當成邊界的過程。
3. **音量上限沒有掛得上的地方,改成一個閘。** 全 stack 沒有任何音量參數:
   `daemon/main.c` 把 miniaudio 播放幀直接寫出,零 gain 級;`/speech/say` 的鍵是封閉的
   (`text`/`id`/`cache` 三個,由測試從 `tts_node.py` 的 AST 導出而不是抄註解 ——
   我第一次就在 guard.py 的 docstring 裡寫成五個,散文裡的數字沒有人在檢查),沒有任何幅度欄位。
   **對一個沒有代碼能設定的參數設上限,就是一個沒有部署路徑的元件。**
   所以落地的是 `test_the_say_request_carries_no_amplitude_the_model_could_ask_for`:
   從 `speech/tts_node.py` 的原始碼推導它讀了哪些鍵,跟普查比對(帶非空下限),
   **第一個給模型一個音量可要求的改動就會變紅**,並且必須為它辯護。
4. **T-C5 那個「指令區與基線位元相同」的 oracle,會被它要抓的缺陷滿足。**
   把資料區塊接到 `instruction_region(base, constitution + data)` 的**憲法參數**上,
   前綴性質**依然成立**,而召回文字已經進到模型讀作規則的那一區。
   我寫的突變體就是這樣活下來的:`assert not startswith(...)` 失敗,因為它**真的**以那個前綴開頭。
   **一個正確版與缺陷版都滿足的觀察不是 oracle。** 所以改成在 `instruction_region()` 裡
   **創造**那個不變量:帶柵欄標記或資料前言的文字**根本不准進這個函式**,
   突變體因此拋錯而不是通過;另外補一條測試斷言那個突變體**確實**保有那個天真的前綴性質,
   把「為什麼觀察不夠」也編進測試裡。
5. **「刪除指令」需要它自己的一格,而且方向是偏精度。** 設計表把刪除寫在 T-C4(級聯執行),
   沒有寫**辨識**。這兩件事的錯誤代價不對稱:誤判成刪除會刪掉別人想留的東西,
   漏判只是對方再講一次更清楚。所以落地的是子句起點錨定 + 一個顯式的否定守衛 + 凍結負例。
   否定守衛是**明知它今天多餘也要寫**:`別忘記` 之所以現在不會被誤判,
   只是因為 別 不是子句分隔符、而 忘 剛好夾在 別 和 記 中間 ——
   那是當前那組交替式的意外,不是防護。**意外的保護不是保護**,
   下一個加進來的模式就會讓「別忘記我說的話」變成一次刪除。

**T-D3 是凍結不變量。** 現有的「事後解析 `[gesture:X]` + 白名單」恰好就是
「reason free, constrain late」:硬 schema 約束解碼可以做到 100% schema 合法
而可執行率從 **91.5% 掉到 48.0%**,而結構驗證器對這種失敗的偵測率是 **0%**。
所以「重構成更乾淨的 structured output / tool use」是退化,不是改善。

**T-D5 的文獻基線:**答案改變 32–86%、錯認自己錯 42–98%、準確率最多掉 27%,
且 correct→incorrect 的翻轉多於反向。

#### 落地時與設計表不同的地方

**1. T-E1 的替身從「會說謊」升級成「不存在」,而探針自己也要被測。**
設計表寫「Bedrock 替身回空字串」。空字串替身能證明的是**代碼在一次壞回覆下存活**;
要證明的其實更強:**這條路上沒有回覆可以存活**。所以改成在子行程的 `sys.meta_path`
上封死 `boto3`/`botocore`/`rclpy`/`websockets`,再跑揭露 latch。
但一個乾淨的探針結果毫無價值,直到你證明它真的到達了代碼——所以旁邊有
`test_the_probe_would_notice_a_blocked_import`:在探針最前面插一行 `import boto3`,
它必須以 `blocked by the probe: boto3` 失敗。沒有這條,一個根本沒生效的封鎖器會讓
主測試綠得一模一樣。

**2. `chant` 不是標記的分支,而這件事要被斷言而不是被列舉。**
設計表把分支寫成「串流、cached、chant、粵語 yue」。讀代碼後:`uid == "chant"`
只決定**可否被打斷**,payload 只是 `uid` 與 `text` 的函式,所以 chant 走的是同一個創造者。
維持這件事的斷言是「`_publish_started` 的識別字裡不得出現 `interruptible` / `_interrupt`」——
比在清單上多寫一行「chant」強,因為清單無法注意到未來的第三條路。

**3. 路由與標記必須是同一次呼叫。**
如果 `started_payload` 用自己那份規則重新判一次引擎,標記就可能寫著一個**沒有發出這段音訊的引擎**。
一個自信而錯誤的標記比沒有標記更糟。證明方式是把 `voices.HAS_YUE` monkeypatch 成永不匹配:
路由與標記必須**一起**改變,而這只有在規則只有一份的時候才會發生。

**4. 瀏覽器抓到兩個 CI 抓不到的缺陷,而其中一個差點變成證據。**
把 `#disclosure` 整條規則刪掉當負對照,瀏覽器算出 `background-color: rgba(0,0,0,0)`——
跟頁面背景 `rgb(16,20,24)` **字串不等、畫面相同**,所以原本比字串的判定式把它判成「可見」。
兩側都修了:瀏覽器側走到第一個 alpha > 0 的祖先,CI 側新增 `_rgba()` 正規化 3/4/6/8 位
hex 並拒絕 alpha `00`,配具名突變體 `background: #10141800`。
第二個缺陷只有**看 PNG** 才會發現:相機串流死掉時 `<img>` 縮成 alt 文字,`#stage` 跟著塌,
絕對定位的 `#hud` 壓到上面兩列,把引擎 id 切一半——當時每一個計算後顏色都是對的。
25 點命中測試從 1/25 與 5/25 降到 **0/25 與 0/25**,兩條 CSS 宣告各配一個突變體。
還有一件必須記下來的:修完之後重測,數字**完全一樣**——reload 吃到快取的舊 CSS,
要 `?v=2` 才讀到真值。**快取頁面不是被編輯過的檔案**,而一個假的量測差兩分鐘就寫進證據檔了。

**5. stub gateway 不放在 `tests/`。**
`tests/test_meta.py` 禁止 `tests/` 下任何模組 import `websockets`,而
`infra/entrypoints.py` 的 `SKIP_DIR_PARTS` 含 `tests`——所以一個網路 server 停在 `tests/` 裡,
恰好落在 check 8 唯一看不見的目錄。它搬到 `web/stub_ws_server.py`,並在
`infra/standalone_entrypoints.tsv` 留一行寫明理由。stub 的 payload 一律由**真正的生產者**
(`disclosure.browser_event()`、`voices.started_payload()`)產生:一個自帶 JSON 副本的 stub
會在生產者改變形狀之後繼續綠,那時瀏覽器是對著一份虛構被驗證的。

T-F4 存在的理由:一個叫 `median` 而實際算 mean 的指標,會顯示一個任何一列資料都沒有的值。
兩個數字就是兩個主張,各自導出,不可互推。

**修正 1(T-F3,狀態不是清單):** 設計表原本只寫「回合仍完成、只用檔案卡」,而那是對**呼叫端**的
要求;檢索器自己回的是一份清單,而一份空清單有四個互不相同的來源——沒有編碼器、磁碟上沒有
artifact、期限用完了、以及真的跑過而且沒有東西符合。**只有最後一個能支撐「0 命中」這句話**,
前三個是「這條路徑沒有跑」。所以每條路徑帶一個狀態,`deletion_findings` 的第一件事就是把
`status != ran` 當成 finding。這條修正的直接後果是 T-C4 的通過標準改了措辭:不是「五條路徑各 0 命中」,
而是「**五條路徑各跑過,而且各 0 命中**」。

**修正 2(登錄冊兩邊都要導出):** 一份五個名字的清單不會注意到第六條路徑。所以路徑只能以
`Retriever._run_<name>` 這個形狀存在,一條測試斷言
`{m[5:] for m in dir(Retriever) if m.startswith("_run_")} == set(PATHS)`——**沒登錄的方法紅,
沒方法的登錄也紅**。另一邊是路徑聲明自己讀哪些 artifact,`coverage_findings(root)` 把它跟
**磁碟上真的存在的檔案**對帳,理由是 `Store.write_snapshot` 收任何一個普通檔名,系統裡不存在
一份 snapshot 枚舉可以拿來導出。

**修正 3(`SEED` 與 `ORPHAN` 是兩件事):** 一筆命中「沒有 episode」有兩個意思,而一個 `None`
會把沒問題的那種跟 bug 那種併成同一格。手寫的種子事實(`profile.TRUST_SEED`)本來就在級聯之外,
乾淨;**該指向某個 episode 而沒指到**的那種是 finding。這條分開之後才擋得住最便宜的作弊:
**刪掉 episodes.json 裡的條目但留著它的事件** —— 每一個對 E 的引用都變成對「無」的引用,
按歸屬檢查的話 E 讀到 0 命中,而文字還在,什麼都沒被刪掉。

**修正 4(卡片事實每個來源都要報):** `Fact.source_episode_ids` 是**複數**。只回 `[0]` 的話,
刪掉第二個來源時卡片會回報乾淨,而那一列還在引用它。所以每個來源 episode 一筆命中,
ref 是 `profile.json#<i>@<eid>`。

**修正 5(不做行程內快取):** 一份撐過刪除的快取索引**就是** T-C4 要殺的那個突變體。
快取是第二個主張(一份失效契約),不是一個最佳化。

**誠實邊界(T-C4 的 harness 必須自己補的洞):** 詞彙路徑會丟掉 0 分的文件,所以一個跟被刪
episode 無關的查詢會從一條**真的跑過**的路徑拿到一個乾淨的零。`deletion_findings` 檢查不到這件事。
T-C4 的 harness 因此必須用**被刪 episode 自己的文字**造查詢,並且斷言那個查詢在刪除之前會命中。

**修正 6(T-F6,缺席資料是一層,不是預設值):** 設計表只寫「三組都要跑」,而三組都跑完之後
最會出錯的地方不是少跑一組,是**一筆無法判斷的命中被當成一個數字**。`end_ts` 缺失填 `now`
會讓沒人標日期的那個 episode 變成全店最新;填 0 會讓它在衰減下低過地板而被刪掉。所以
`memory/rank.py` 不接受任何預設值:六個新鮮度狀態(`DATED`/`UNDATABLE`/`FUTURE_TS`/
`NO_EPISODE_BY_DESIGN`/`LOST_ATTRIBUTION`/`NO_ENTRY`)與五個重要性狀態(`SCORED`/`NO_SALIENCE`/
`OTHER_FORMULA`/`UNSCORABLE`/`NO_RECORD`),`Freshness`/`Importance` 兩個型別在建構時就拒絕
「宣稱缺席卻帶著一個值」與「宣稱有值卻沒帶」。`_tiered()` 把每條路徑切成一個**可比較層**
(可重排、可丟)與一個**不可比較層**(留在基線順序),兩層的邊界就是這條修正。

**修正 7(那個逐位元相同的突變體,以及它逼出的 fixture 設計):** 「缺席的 salience 當 1.0」
剪掉的命中與真品**完全相同**——同樣的順序、同樣的丟棄。一份比對命中集合的測試會判它死,
而那是量錯了東西。所以那一條斷言下在報告上:真品回報「kept unjudged」,突變體什麼都不說。
同一個算術也決定了 fixture:排序鍵是 `weight / (1 + position)`,而**位置那一項是主導項**,
所以「`end_ts` 缺失當成 `now`」這個突變體只有在那筆不可判斷的命中**本來就排在基線第 0 位**時
才觀察得到——它排在後面的話,錯誤的預設值產生的輸出逐位元相同。第一版 fixture 把它放在
seq 3,那個突變體活了下來而測試是綠的。兩筆事件的排序 fixture 同理:6 天 vs 1 天不會交換
(0.5518 > 0.4529),要 14 天 vs 0 天(0.25 vs 0.5)才會。

**修正 8(碰撞判定需要一個反控,而且不能靠讀自己的 log):** 三支臂輸出完全一致 = 一支臂
報了三次,但在**只有一筆命中**的 store 上那是**預期狀態**。所以 `identical_arms()` 回的是資料
不是訊息,嚴重度由 `verdict()` 從 `report["identical_arms"]` 聚合:一條查詢上碰撞是 note,
**每一條查詢都碰撞**才是「同一個政策掛兩個名字」→ 結構性 → exit 1。測試兩邊都有:一個
一筆命中的 store(碰撞,exit 1)與完整 fixture(不碰撞)。

**誠實邊界(T-F6 今天能證明什麼):** 只能證明**三支臂彼此不同、而且各自讀了自己聲稱的信號**。
它不能說哪一支更好——那是 T-F1 的 30 條凍結查詢,需要一天真實日誌加一次人工標註,兩者都不得
編造。所以 `quality` 是狀態 `NO_LABELS`、`conclusion_blockers` 今天永不為空、harness 退出 2,
而這三件事本身都是**被測到的性質**,不是文件裡的一句註記。§6.5 那條「沒有任何論文做過
decay vs no-decay 的 ablation」仍然成立:這個 harness 比出的是我們自己的偏好。

### G. 輸出守衛(S7)

**修正 1(串行守衛要在 API 裡不可表達,不是在測試裡被勸阻):** 計畫寫的是「守衛必須異步」,
而一條量延遲的斷言在筆電上量的是筆電——`assert diff_ms <= 50` 在一台忙碌的機器上會紅,
在一台閒置的機器上會綠,兩次都跟守衛是不是異步無關。所以 `OutputGuard.offer()` 標註成
`-> None` 且函式體裡沒有任何帶值的 `return`,而一條 AST 測試斷言這件事。裁決只有一條路能
進來:後來的 `verdict(uid, index, blocked=…, now=…)`,按 span 對號。**呼叫端沒有地方可以
「等一下」**,因為沒有東西可以等。在機的 50 ms 那半仍然要跑,但它量的是回歸,不是設計。

**修正 2(可聽度是四級,不是布林):** 「擋下了嗎」這個問題在一個異步守衛裡沒有答案。
四個值各有不同的意思,而它們的差別就是這一節的全部價值:

| 值 | 意思 | 中斷欠不欠 |
|---|---|---|
| `SILENT` | 裁決比第一塊音訊早到 | 欠(還沒出聲,清掉播放環是免費的) |
| `PARTIAL` | 音訊開始了,中斷把它切掉 | 欠(**這是正常情況**,p50 749 ms 保證了它) |
| `FULLY_AUDIBLE` | 播完了,守衛什麼都沒擋住 | **不欠**——這時發中斷會把**下一句**切掉 |
| `NOT_SPOKEN` | 說話者自己丟掉了(快取未命中、佇列滿、session 結束) | **不欠**,而且不是守衛的功勞 |

把 `FULLY_AUDIBLE` 併進「擋下」是讓「0 逃脫」失去意義的那個謊:一個從頭到尾播完的句子
被記成擋下,報告就會在守衛完全失效的時候顯示滿分。所以稽核記錄的 `decision` 只有在**真的發出
過中斷**時才是 `"blocked"`,否則是 `"recorded"`。四級**每一級都有一條測試證明它可達**,
因為一個永遠走不到的分支等於一個不存在的分支。

**修正 3(`NOT_SPOKEN` 必須被告知,不能被推論):** 從守衛裡面看,「還沒出聲」與「永遠不會
出聲」是同一個「沒有音訊」,而結論相反。所以說話者要呼叫 `abandoned(uid, index, now=…)`;
守衛不猜。把說話者自己丟掉的句子算成守衛擋下的,會把一次中斷寫成一份聲稱擋了五句的報告。

**修正 4(五個決策狀態,而 error 不是 allow):** `blocked=None` + `error="…"` 是分類器失敗
進來的形狀,它落在 `ERRORED`,逾時落在 `TIMED_OUT`(按規則 4 單獨計數,永不算成錯誤)。
把「不知道」當成 `ALLOWED` 就是在紅隊最會去踩的那個網路抖動上 fail open。

**修正 5(2.0 秒的期限是導出的,不是選的):** `VERDICT_DEADLINE_S = 2.0` 是
`MEASURED_MAX_MS = 921.2` 的 2.2 倍,而那個 921.2 是 T-K3 在 **ap-southeast-1 我們自己量的**
(`docs/evidence/track-c/guardrail-latency.json`),不是別人的 client-side n=15。一條測試分兩件
事斷言:`MEASURED_MAX_MS` 等於 `max(g["max_ms"] for g in measured["pooled"]["groups"].values())`,
以及期限大於它的兩倍 —— 兩個數字兩個導出,所以重量之後兩個都不會偷偷留在原地。外部那組數字(p50 **749** / p90 **907** / max **1837 ms**,
client-side,n=15,按規則 4 它的 p95 沒有意義)仍然是為什麼串行前置一定會把首句推到接近一秒。

**修正 6(守衛的單位是說話者命名的 span,不是守衛自己切的句子):** 斷句規則在這個系統裡已經
有兩個讀者——Kokoro 的 `KPipeline` 在一條路上擁有邊界,`re.split(r"(?<=[。!?!?;;])")` 在
`yue` 那條路上擁有邊界。守衛再寫第三條就是「兩個 parser 讀同一個格式」的缺陷,而它的可觀察
後果是中斷打到錯誤的句子。所以 `safety/output_guard.py` **不得 import `re`、不得呼叫
`.split()`**(AST 斷言),span 的身分是 `(uid, index)`,`index` 由說話者給。

**修正 7(逃脫數不能跨類別池化):** 七個類別裡有兩個(`identity_denial`、`boundary_override`)
在輸出側**沒有執行者**——Guardrails 的內容過濾器沒有這兩個類別,而 `PROMPT_ATTACK` 只作用在
輸入側。一份把七個類別的逃脫數加起來除以 50 的報告,會用五個類別的成績蓋掉兩個完全沒有防護的
類別。所以 `ENFORCERS` 把類別對到執行者,沒有執行者的兩個對到 `NO_ENFORCER_TODAY`,
`escape_report()` 給它們 `block_rate: None` 加一個狀態,而 harness 的 `verdict()` 把它們算成
**不能宣稱覆蓋**(exit 2)而不是缺陷(exit 1):那是系統的缺口,不是這次跑的缺陷。

**修正 8(粵語是狀態,不是比率):** `LANGUAGE_SUPPORT` 把 `yue` 標成 `NOT_SUPPORTED`,
`escape_report()` **拒絕**為它算 block rate,只回計數。一個被擋下的粵語句子是關於一個字串的
一次觀察,不是「粵語被保護」。這條在文件裡是一句話,在代碼裡是一個會紅的突變體。

**修正 9(`chant` 是跨兩個命名空間的共用 token,所以普查必須是兩個主張):**
`body/gestures.py:76` 的 `Gesture(name="chant")` 是一個**手勢**名字,不是話語 id ——
它由 `chant_pump` 建構,而且**不是 `GESTURES` 白名單的鍵**,所以模型寫 `[gesture:chant]` 也到
不了它。第一版的普查只看字串值,於是被這一處判紅。**正確的反應不是給偵測器一個豁免**,
而是承認這是兩個不同的主張:寬的那個(這個字串在哪裡出現過)對三個檔案精確集合相等、每一處
都寫下理由;精確的那個(出現在**話語 id 位置**的 `chant`)只允許 `game/game_node.py`。
一個被放寬過的偵測器,下一個同名 token 就從它放寬的那個縫裡進來。

**修正 10(exit 0 不可達,而且被斷言不可達):** 跟 `memory/rank_harness.py` 同一個形狀。
今天七個類別有兩個沒有執行者、兩種語言有一種官方不支援,所以 0 在結構上不可能;一條測試
**對真實的凍結集**斷言這件事,理由是 0 是讀者會引用的那個數字。`verdict()` 讀的是**完成後的
報告**,所以把 JSON 重放一次會得到逐位元相同的退出碼。

**誠實邊界(S7 今天證明了什麼、沒證明什麼):** 證明了守衛的**協定**——什麼時候欠一個中斷、
一份稽核記錄可以宣稱什麼、哪些類別沒有防護、哪些語言不能宣稱。**沒有**證明任何延遲:
裁決→靜音 ≤ 400 ms 與首句差值 ≤ 50 ms 兩條都需要機器,而機器今天在 SSH 隧道那一邊,
擋在安全群組的 `/32` 上。也沒有證明凍結集擋得住:那要 `--guardrail-id` 的真跑。
規則 3 仍然是這一節的天花板——50 條 0 逃脫是**曝露的下限**,永遠不是保證。

與 `docs/evidence/track-b/arm-cost.json`(`choose()` 逐次成本,只報不閘)。

閘是一個 **e-value**(帶 Ville 保證)而不是 p-value。H0 是「使用者下一手在
{rock, paper, scissors} 上均勻,且與之前一切可觀察量獨立」。在 H0 下,任何**可預測的**
預測分佈 q_n 都使 E[q_n(x_n)/(1/3)] = 1,所以連乘積是均值 1 的非負 martingale;
用 Dirichlet(1,1,1) 序列預測器,那個連乘積在計數上有封閉形式(Dirichlet-multinomial):

    E_k = ∏_contexts [ 2 · ∏_m n_m! / (n_c + 2)! · 3^{n_c} ]

Ville 不等式給 `P(曾經 E ≥ 1/δ | H0) ≤ δ`。**這是為什麼沒有做多重比較校正,也不需要**——
聚合發生在 martingale **內部**,不是跨多個獨立檢定;若走 per-context union bound,
δ_c 會是 0.05/7371 ≈ 6.8e-6,那是把一個正確的推論換成一個保守到沒用的推論。
order 2..4 用**平均**合併,因為 e-value 的平均仍是 e-value。

落地時有九件事跟設計表寫的不一樣,**三件是設計表的通過標準本身錯了**(修正 1、2、7):

**1. T-H2 ③ 的「移除信賴閘 → 必須紅」在原理上做不到,不是沒實作。**
猜拳的payoff矩陣是零和且對稱,所以面對均勻 i.i.d. 對手,**任何**機器人策略的期望分數
恰好是 0。要求「拿掉閘之後均勻那一案在**分數**上變紅」,是要求一個數學上恆為 0 的量變負。
實測:未設閘的 diff **−0.0086**,CI [−0.0204, +0.0032](n=100 seeds)——
符號方向與文獻的 −0.0085(a−2) 風險一致,但離 0 只有 1.4 個標準誤,拿它當 CI 閘會是 flaky。
所以判別斷言改成**閘本身**:曾開啟過閘的 seed 比例,設閘 **3/100 = 0.03**、
未設閘 **100/100 = 1.00**。這個量在突變體下移動 33 倍,而且它直接就是 δ = 0.05 的實測驗證
(Binomial(100, ≤0.05) 的 99.9 百分位是 12,所以斷言寫成 ≤ 0.12 而不是 ≤ 0.03)。

**2. T-H2 ④ 的「閘開啟比例 < 10%」是經驗上錯的,而真相比那個標準好。**
實測:面對會適應的反學習者,閘在 **71.1%** 的回合是開的,而模型**贏** +0.0931/局,
CI [+0.0829, +0.1033]。我原本(寫在模組 docstring 裡)預測閘會關著——**被自己的量測證偽**。
機制是迴路閉合:機器人的出拳是使用者自身歷史的函數,所以一個對機器人反應的對手,
**因此就是**在對那段歷史反應,於是從那段歷史就預測得到它。在這裡保護我們的不是閘,
而是「比對手更難被建模」。兩個誠實邊界:那是一個特定的反學習者(A 級,單邊 oracle,§5),
而且整件事是機器對腳本,裡面沒有人。所以 ④ 的通過標準只保留「分數不顯著低於 0」,
開啟比例改成**記錄值**,並在測試裡斷言它 > 0.5 —— 讓「有人把它改回關著」也會紅。

**3. 閘有價格,而且量到了。** 在可被利用的對手上,未設閘的那一臂每局分數**高** 0.3–0.9 pp
(0.5541 vs 0.5508;0.2193 vs 0.2099),因為閘把開場的回合花在證明它後面才要用的東西。
這不是缺陷,是明碼標價:用 0.3–0.9 pp 換一個對均勻對手的 δ = 0.05 終身誤開上界。

**4. 結構性稀疏:上下文字母表是 9 個符號(3 手 × 3 勝負),所以 order-2 就有 81 個桶**,
order-3 是 729,order-4 是 6561,而 backoff 在 order-2 底下沒有更矮的一級。
一場 20 局的 demo session **在算術上不可能**填滿 81 個桶中的任何一個到
`min_context_count = 3`。實測第一次預測落在**第 ≤120 局**;20 局的 session 必然回 `None`
(即回均勻 1/3,這是安全的方向)。這件事寫成 `test_the_warm_up_cost_is_bounded`
而不是靠加一個 order-1 rung 調掉——因為 T-H4 顯示 order-1 在我們的 fixture 上領先
(條件均勻 0.8283 vs 0.6393;win-stay 0.7613 vs 0.5508),**但那些 fixture 本身就是
order-1 過程**,所以這個量測沒有裁決權。要改 order 集合得用真人資料,
不能在合成 fixture 上調參。

**5. 一個浮點求和順序的缺陷,方向是「從磁碟還原後開了一個重播時關著的閘」。**
每個 context 的貢獻是快取的(否則 300 局 × 100 seed × 11 run 要 ~10⁸ 次 lgamma,
跑不完就不會有人跑)。第一版用一個累加的running total:它按**回合**順序累加,
而從表重建是按**context**順序累加,浮點加法不可結合,兩者差在最後 2 個 ulp
(實測 35.963475426014185 vs 35.96347542601416),而這個值接著去跟閘門閾值比大小。
修法是快取**每個 context** 的值、總和用 `math.fsum`(精確求和只捨入一次 → 與順序無關)。
同時把 `history` 裁到最後 max(orders) 局:只有那幾局能構成 context,狀態因此有界,
而 `from_dict` 對更長的 history 直接拒絕(那不是 `to_dict` 寫出來的東西)。

**6. 一個會自我修復的診斷不是診斷。** `evidence_matches_recomputation()` 最自然的寫法是
「重建一次,比較前後」——而它**因此修好了它負責偵測的漂移**。實測:陳舊快取那個突變體
先老實回報漂移,然後 `gate_open()` 通過,因為問這個問題已經把答案改掉了。
改成純唯讀比較之後突變體才死。規則 2 的推論:**一個不能放在斷言前面的診斷沒有用途**。

其餘設計時就成立、實作後確認的兩點:T-H3 把第七輪的修正編進測試——人類猜拳的**邊際**分佈
(0.36/0.33/0.32,354 人 × 300 局)與 1/3 統計上不可區分,所以**移動頻率計數器沒東西可利用**;
fixture 的邊際實測 0.3389/0.3302/0.3309,先驗過 |p−1/3| < 0.02 才允許它當 T-H3 的對手,
否則「條件結構被利用」可能只是邊際被利用。而 context 一律鍵在**使用者自己的**
(手勢, 勝負) 對上,**從不**鍵在機器人的出拳:鍵在自己的出拳等於給反學習者一根槓桿,
讓它可以操縱「它被預測時所用的那個 context」。

**7. T-H6 的「p95 抖動 ≤ 現值 + 5 ms」跟本檔 §3 的房規直接衝突,而房規是對的。**
§3 寫著「沒有任何測試斷言執行時間」,理由是一個會因為機器忙而變紅的測試兩天內就會被加上 skip。
一個計時閘門在這裡還多一層問題:它量的是**筆電**的抖動,而節拍實際跑在 EC2 上,
所以就算綠了也沒有回答「節拍會不會飄」。改成一個**結構式**的 oracle:
從 `game/game_node.py` 的 AST 導出方法層的呼叫圖,取節拍入口 `on_tts_started` 的可達閉包,
與「碰得到 `self.opponent`」的方法集合取交集,斷言那個交集是**空的**。
這個問法在筆電、EC2、和任何負載下都給同一個答案,而且它閘的是設計不變量本身
(推論在 arm 時發生一次,節拍只播已經決定好的手)。
`tick` **不在**入口集合裡——它經 `resolve` → `_learn` 合法地碰到模型;那條路徑改用
語句順序斷言覆蓋(`_learn` 必須排在結果播報與 banter 請求**之後**)。
抖動數字仍然要量,只是**只報不閘**:`--arm-cost` 寫出 `arm-cost.json`,
實測 p50 **0.0082** / p95 **0.0113** / max **0.1137** ms(n=2000,258 個 context,
表由 300 局真實回合暖機)。max 是一個 20 ms 節拍週期的 **0.57%**,而且它根本不在節拍上。

**8. 一個結構閘不能拿寫下來的清單當交集的一邊。** 第一版的 `beat_path_leak` 是
「`on_tts_started` 的可達閉包」對照**手寫的** `MODEL_METHODS`,而那個版本被自己的突變體殺穿:
把 `self.opponent.predict()` **inline** 寫進 `on_tts_started`,不會產生任何新的**具名**觸碰者,
所以閉包裡沒有多出東西,檢查照樣綠。修法是兩邊都導出——
`reachable(entry, methods) & touchpoints(methods)`。這是「名單注意不到新名字」那條規則
在呼叫圖上的形態,而抓到它的不是複查,是那個突變體存在。

**9. 把重複的不變量收成一份,改的是測試不只是代碼。** 舊的 `WINS` 表(在 `game_node` 裡)
與 `BEATS`(在 `opponent` 裡)是同一個關係的兩份拷貝,原本有一個跨檔一致性測試守著它們。
`game/rps.py` 落地後 `WINS` 被刪掉,那個測試就**不可執行**了(它 `literal_eval` 一個不存在的名字),
而一個前提失效的測試會以 `TypeError` 的形式紅——這是對的方向,但它不再測任何東西。
替代品換了形狀:斷言那份拷貝**不存在**(`game_node` 模組層沒有任何猜拳配對字面值),
並斷言僅存的那個創造者(`rps.judge`)真的**被用到**——
規則是「找出創造不變量的那一行」,而不是比對兩份拷貝有沒有一致。
它的突變體也跟著換了主張:翻轉 `BEATS` 現在必須讓 `rps.judge` 的判決**跟著動 9 對裡的 6 對**,
證明的是**委派**(如果 `rps.py` 悄悄長出自己的拷貝,那 6 對就不會動),不再是分歧。

還有一個不在上面九條裡、但同一形狀的缺陷,因為它屬於 `rps.majority` 而不是設計表:
**平手時的贏家原本由 `set` 的迭代順序決定。** 三手各出現一次時,`list(set(window))[0]`
在不同 `PYTHONHASHSEED` 下給不同的手,而那是一個**跨行程不可重現的紅**。
改成按 `MOVES` 的宣告順序斷開平手之後,`test_majority_is_stable_across_hash_seeds`
在 8 個 hash seed 下子行程重跑並要求答案恆為 `rock`;同一個測試裡帶一個**對照**:
`list(set(window))[0]` 在那 8 個 seed 下必須**真的不同**——哪一天 CPython 讓字串 set
的順序與 seed 無關,這個測試就會紅而不是默默失去意義。

**接線已經落地**:`game/game_node.py` 現在在 arm 時問模型(`_arm`),
每局結果 fire-and-forget 發到 `/game/rps_round` 交由 `memory_node` 落盤(單寫者不變量),
並訂閱 latched 的 `/memory/rps_table` 還原累積表——`from_dict` 拒絕的狀態一律整份丟棄,
不做部分合併。前提條件(T-H2/H3 全綠)在接線之前就已達成。
修正 4 的熱身數字**不是這一輪要調掉的東西**:20 局的 demo session 仍然會回均勻 1/3,
那是安全的方向,而要改 order 集合得先有真人資料。

**T-J11 的動機跟 T-J10 完全同一條,只是這次在還沒炸之前就找到了。**
`Hit.ref` 不是標籤,是 join key,而且它的三個消費者都不呼叫寫出它的那段程式:
`deletion_findings` 把它印進 receipt、`memory/erase.py` **重建**卡片與 RPS 的 ref 去比對
`recall.py` 產出什麼、S6 的排序臂要靠它把一個 hit 接回帶著 salience 的那筆事件。
普查當時的結果是**兩個生產模組共九個產生者**(`recall.py` 六個、`erase.py` 三個)——
跟 `.push/files.txt` 一模一樣的形狀:兩個寫者對一個格式只在沒人動其中一個的期間同意。

所以斷言不是「已知的九個呼叫點都改用建構函式」——**一份九個位置的清單不會注意到第十個**。
斷言是對那個**形狀**的普查,四個建構函式是唯一的白名單,而白名單的行號從 AST 取,
所以搬動或改名建構函式會把豁免一起搬走,不會默默變寬。
非空對照放在最前面:偵測器必須先看得見四個建構函式自己,一條命中零次的普查
對「零個違規」什麼都沒證明(§0 規則 5)。

**T-J10 是這一輪被一個 exit 3 逼出來的,而缺陷在格式而不在任一個讀者。**
`.push/files.txt` 有兩個讀者:`push_branch.py` 推它,`redact_scan.py` 掃它。
`parse_files` 跳過 `#` 註解(docstring 裡就寫著),`read_list` 不跳——它把
`# T-C5 的注入半段:…` 切成一個模式加一個路徑,然後回報
`CANNOT RUN: listed path is not a file`。這個 PR 是第一份帶註解的清單,所以這條分歧
在此之前一次都沒出現過:**先前每一份清單都恰好只用了兩個讀者都實作的那個子集**。

值得說清楚失效的**方向**:它是 exit 3,不是一次假的乾淨。脫敏閘拒絕跑,而不是掃了零個
檔案還報 0 findings——`read_list` 對每一列都要求檔案存在,而註解不是檔案。所以這條分歧
不曾讓任何未脫敏的位元通過,它只是讓一份沒問題的清單推不動。但**一個只有兩個讀者中的
一個實作的格式不是格式**,而下一次分歧沒有理由一定落在安全那一邊。

修法在格式層而不在其中一邊:`read_list` 跳過空行與 `#`,並且測試斷言的是**兩邊同意**,
不是各自的行為——一條只釘一邊的測試會在另一邊移動時繼續綠。剩下的不對稱是刻意留著的:
`parse_files` 還多拒絕非數字的模式,所以它嚴格更嚴,而更嚴的那一邊拒絕的清單等於一次
不會發生的推送——那是安全的方向。

那個突變體(拿掉 `startswith("#")` 那半)也示範了 §0 規則 2 的另一面:它的施加器
`load_mutant` 把 `importlib` 的兩行**寫在自己身體裡**,而不是委派給旁邊的
`_load_module`。理由是 T-J7 的偵測器**推導**什麼算施加器(改寫文字**且**把結果變回
程式),而一個改完文字、把復活交給被呼叫者的 helper,恰好是偵測器看不見的施加器——
也就是當初 `test_guard.py` 那 10 個未標記案例重演一次的形狀。

T-J6 掃的對象是 `.push/files.txt`——**即將被推上去的那份清單**,而不是 `git ls-files`、
不是工作樹、也不是 `git diff --name-only`。這三者回答的是不同的問題,而在一個
「只走 Git Data API、沒有本地 git repo」的專案裡,只有清單才等於「我現在要公開什麼」。

它自己建置過程中出過兩個缺陷,兩個都是同一個形狀:

**1. 崩潰與命中在退出碼上長得一樣。** 未預期的例外一律映射成 exit 3,是因為 traceback
也是 exit 1。實測:在掃描器其實正在因為打不開清單檔而崩潰的時候,陽性對照對
**七個模式類全部報「殺掉」**,無突變對照報「有命中」——每一個訊號都看起來對,而沒有一個是真的。

**2. 守衛會掃到自己,而且掃得對。** `pem path` 的模式一開始寫成零或多個前綴字元,
於是**只要提到那個副檔名**就命中——第一個被它抓到的就是掃描器自己與它的測試。
把前綴改成一或多個之後,它又抓到我在測試 docstring 裡引用的一個「像樣的」金鑰路徑範例。
兩次都是同一條規則的反例:**描述模式,絕不重現模式**;可命中的字串只在
`_secrets()` 裡於執行期組裝,從不落成原始碼字面值。

**T-J7 是這一輪才發現需要的,而發現的方式是我自己違反了它。** §3 說 L3 是
`pytest -m mutation`,§0 規則 2 說每輪都要跑全部具名突變體加一個無突變對照 ——
這兩句只有在「每個施加突變體的測試都帶 marker」時才成立,而沒有任何東西在檢查那件事。
實際狀態是 `test_guard.py` 的 10 個案例與 `test_game_wiring.py` 的 9 個
(8 個突變體 + 那個對照)**兩個檔案都沒標**,所以 `pytest -m mutation` 兩個都沒跑。
**一輪漏掉一個突變體不會報缺口,它會報通過。**

偵測器**由機制推導,不是列名字**:一個突變體施加器是「改寫原始碼文字」**且**
「把結果變回程式」的函式 —— 兩個條件都必須,因為只改文字的是字串工具、
只 import 的是載入器,而兩者的合成才是施加器。這個 repo 現在有兩個,
名字叫 `load_mutant` 與 `mutate`;**一份手寫的名字清單不會注意到第三個名字**。
下限斷言(模組數 ≥ 4、突變測試數 ≥ 25)是為了同一件事的另一面:
把施加器改名到偵測器看不見的地方,結果會是一份「零個未標記」的乾淨普查,
而那讀起來跟合規一模一樣。

T-J5 在 Darwin 上沒有 `/proc`,讀不到行程的 text inode。換的問法是同一件事:
**在行程啟動之後才被寫入的執行檔,不是正在跑的那個 image。**
`ps -o lstart=` 就足以回答,而那個時間戳的解析本身也有一個測試——
一個靜靜拋 ValueError 的解析器會讓這個檢查永遠 skip。


**T-J8 也是我自己違反了才發現的,而且是同一天違反兩次。** §0 規則 6 說「數字由 harness
輸出,文件引用 harness」。實際狀態是:§0 表格寫著 `tests/test_meta.py | 25`,
而它下方四行的散文說那個檔案的離線 import 掃描「從 17 一路走到 23」——
同一個檔案的兩個數字,不可能都對,而全套測試是綠的。同一批數字(全套案例數、突變數)
還被抄在 `README.md` 與 `README.zh-TW.md` 各一次,所以任何一個新增測試的 PR
都會同時作廢三份文件裡的五個手打數字。

它上線的第一次執行就抓到 11 條不符,其中有一條是我**沒想到**的:
`tests/test_meta.py` 從 28 變成 29 —— 因為它的離線 import 掃描是對目錄參數化的,
我新增 `tests/test_doc_counts.py` 這個動作本身就讓它多一個案例。
「文件裡的數字會被自己的存在改變」正是手動維護做不到的那一類。

兩個設計決定值得寫下來:

1. **讀不到句子必須是 finding,不能是「沒事可檢查」。** 否則把 `Offline suite, N cases`
   改寫成 `Offline tests, N cases` 就等於安靜地關掉那一項檢查 —— 跟掃到 0 個檔案卻退出 0
   同一個形狀(§0 規則 5)。**句子出現兩次也是 finding**:檢查器讀一份、讀者讀另一份,
   正是 25-vs-23 那對數字活下來的方式。
2. **迴圈跑「表格 ∪ 收集到的」的聯集,不是表格本身。** 一份寫死的清單對新名字天生看不見;
   跑表格的那個版本就是 `test_mutant_iterating_the_table_cannot_notice_a_name_it_does_not_contain`
   要殺的突變體。
3. **一列有兩個數字,而其中一個從來沒有讀者。** §0 表格每一列同時說「這個檔案收集幾個案例」
   與「其中 L3 選到幾個」,而 R0b-2 之前只有前者被對帳過。加上後者的第一次執行抓到三條:
   `tests/test_consolidate.py` 那列寫 `L3 選到 13 個:12 個具名突變體 + 無突變對照`,
   而那一層收集到的是 **12**(11 個具名突變體 + 對照)——多算的那一個是紙上的;
   另外兩列(`tests/test_deploy_path.py`、`tests/test_redact_scan.py`)**根本沒寫總數**,
   只寫了具名突變體的分解(17 + 1、8 + 2),所以收集數沒有任何數字可以跟它不一致。
   **一個分解不是一個總數** —— 17 + 1 要讀者自己加起來才是 18,而閘不會加法。
   兩個方向都查:一列替一個**收集不到任何突變體**的模組宣告 L3 總數,正是一個被刪掉的
   突變體留下來的形狀,而它讀起來像覆蓋率。
4. **同一個數字寫在表格裡也寫在散文裡,而表格檢查只讀表格。** 這正是 25-vs-23 那一對
   四行之隔還能活下來的原因。所以 `` `tests/test_x.py` N 個案例 `` 這個句型由**文件本身**
   掃出來,再逐一對收集數;今天有七處,而**七這個數字刻意沒有被寫下來** ——
   迴圈讀文件說了什麼,所以下個月新寫的段落在寫下的那一天就被檢查,而一份句子清單做不到。
   零處是 finding(§0 規則 5 的 `ran` flag):零處代表句型被改寫了,永遠不代表文件不再引用案例數。

**T-J9 是在組 S3 那次推送時當場踩到的,而且五個既有檢查全部會放它過去。**
`.push/push_branch.py` 早就會斷言「建出來的 tree 裡每個 entry 的模式等於請求的模式」——
但那句話比對的是**它自己要求的那個模式**,所以對一個寫錯的要求天生無效。
`.push/files.txt` 其他每一行都是 `100644`,於是替 `infra/run_ec2.sh` 也打 `100644`
是最自然的動作,而它會**把節點啟動器的可執行位元剝掉**:blob 的三個 sha 一致、
tree entry 與請求相符、read-back 與本地位元組相符、脫敏掃描乾淨、全套測試綠。
缺陷在一個乾淨 clone 上以 `permission denied` 現形 —— 也就是在部署路徑上,
這個 repo 已經被同一個位置咬過一次(§0-2 的 `yue`)。

兩個設計決定:

1. **離線那一半才是主要的守衛。** 本地檔案就在手邊,所以「清單說 100644、磁碟說 0755」
   這件事不需要問 GitHub 任何事情就能判定,`tests/test_push_branch.py` 因此能對
   **真正那份 `.push/files.txt`** 直接斷言 —— 它就是那條在 `infra/run_ec2.sh` 上變紅的測試。
   線上那一半補的是另一個洞:一個模式從 base 漂掉、而本地磁碟也跟著漂掉的情形。
2. **只比可執行位元,不比整個模式。** group-writable 對 git 而言仍然是 `100644`,
   比整個模式會讓守衛在一個 git 根本記不下來的差異上變紅,而那是守衛被關掉的方式。
   反過來說,`chmod +x` 不是 umask 會不小心做出來的事。

**base 樹的遞迴列表也檢查 `truncated`。** 一份被截斷的列表是對「base 有哪些模式」
更短的回答,而缺席的路徑會被讀成「這是新檔」—— 正好就是這個守衛放行的那一類。

S7 的整個非同步設計、§0-8 的延遲主張、S5 的 150 ms 期限,
**目前都建立在別人的數字或沒有數字上**。

**修正 1(T-K3,設計表被推翻的一條):** 計劃書把 Standard tier 當成一個可以打開的設定。
量測發現**沒有 cross-Region inference 就開不起來**:照直覺建出來的護欄是 Classic,
而 Classic 只有 en/fr/es —— 一個這台機器人一種語言都不說的 tier。
所以 tier 現在**從控制面讀出來**而不是寫在 harness 裡。這一條的價值不在於數字,
在於它揭露了原本的斷言是空轉的:`"tier": "STANDARD"` 是個字面字串,
`assert evidence["tier"] == "STANDARD"` 於是永遠綠,而底下量的是錯的 tier。

**修正 2(T-K3):** 我們自己的 p50 是 **415.8–435.4 ms**、p95 **498.7–531.6 ms**(pooled n=60/組),
比 S7 引用的第三方 p50 749 ms **低約 44%**。但三組**都超過 400 ms 的 S7 預算**,
所以 S7 的「非同步 + 殺聲」設計**存活**——它的前提只需要「這個呼叫大到不能串行」。
另外:語言之間的 p50 差距 19.6 ms **小於**同一組重測的 95% 上界 40.6 ms,
所以**這份資料不支持任何「某個語言比較慢」的說法**。
比較的標尺必須是重測區間的**最寬界**,不是它的點估計——
純噪音的點估計接近 0,拿點對點比會讓幾乎任何差距都看起來是真的。

**修正 3(T-K5,設計表的問題本身被推翻):** 計劃書問的是「§0-8 的延遲改善是否為真」,
只留了是/否兩個答案。量測的答案是**問題問錯了**:首 token 延遲的差是
+48.3 ms 而 95% CI [−6.5, +95.8] **跨過 0**;而同一個參數**確實被讀**——
它改的是**生成長度**,不是首 token 時間。對句級流式 TTS 來說,
這代表 `effort:"low"` 買不到「開口更快」,買到的是**回合更短 + 輸出成本更低**。
所以結論句有三個出口不是兩個:「延遲有改善」/「被讀了但指標指錯」/「沒被讀」,
而中間那個出口如果不存在,一份「無效果」的量測就跟「這個欄位被默默忽略」
長得一模一樣,兩者要做的決定卻正好相反(換指標 vs 別再送這個欄位)。

**修正 4(T-K5,我自己的第一版被自己的量測推翻):** M3 一開始跟 M2 共用同一個 prompt,
理由是「兩個量測應該講同一個 workload」。跑出來三個條件全落在 112–263 output tokens、
範圍完全重疊 —— 因為那個 prompt 寫著「用三句話」,**長度是 prompt 定的,不是 effort 定的**。
一個把自己要量的量給釘死的 prompt,會讓 honoured 與 no-op 產生一樣的證據,
而那正是 M3 存在要排除的混淆。修正是 M3 改用不含長度指示的開放問題,
並且 `no_length_instruction` 是一個**測試**而不是一句註解。

**修正 5(T-F5):** 中文的 `tokens_per_char` 量到 **0.98–1.03**,
也就是說對中文而言字元上限**幾乎就是** 1:1 的 token 上限;
`proxy_over_real` 兩個樣本是 0.7695 / 0.8051,對上 skills 的 0.79 ——
**同一個校準在第二段不相關的文字上複製成功**,所以 repo 裡只需要一個代理。
憲法本體的常駐成本是 **1076 tokens**(1096 字元),與檔案卡的 350 token 預算是兩筆帳。

**未做的三條共同的阻塞原因:** T-K1/T-K2/T-K4 都要跑在 EC2 上,
而目前的安全群組不含這台筆電的出口 IP。開一條 `/32` 是**權限放寬**,
必須由人授權;SSM 沒有退路(instance profile 有,agent 沒註冊)。
**這三條不是「跳過」,是「被擋住」,狀態欄寫「未做」而不是留白就是為了不讓它們消失。**

### L. 工具邊界(S8 的離線半段)

計劃書的 S8 那一列在測試欄寫的是「之後再設計」,所以這一節是新設計而不是照抄。
設計它的第一件事是讀今天的代碼,而讀完得到五個**已驗證的缺陷**——不是想像的風險:

| # | 今天的事實 | 為什麼 MCP 之後會變成缺陷 |
|---|---|---|
| 1 | 「模型能碰到哪些工具」由 `skills/loader.py` 的一個 dict 回答 | MCP 之後由**另一台機器在執行期**回答,離線套件於是**結構上失去**斷言這個邊界的能力 |
| 2 | `toolConfig` **只在技能命中的回合**掛上(`agent_node.py:213`) | 常駐工具目錄把它變成**每一回合都付**的輸入成本,而 T-I1 的每技能 150 token 預算沒有對應的工具規格版本 |
| 3 | `MAX_TOOL_HOPS = 3` | 它界的是**讀取次數**;三次讀檔是三次讀檔,三次遠端工具可能是三個動作,其中兩個收不回來 |
| 4 | `run_tool` 對所有失敗回同一個 `(f"unknown tool {name!r}", False)` | MCP 之後「模型編了個名字」/「伺服器不再提供」/「連不上」/「政策拒絕」印出同一行,於是**網路故障會被記成「邊界守住了」** |
| 5 | `safety/output_guard.py`(整個 S7)在 `tests/` 之外**零呼叫者** | 語音是四個 topic 加一個工具通道裡**唯一**被討論過的那條,而 MCP 再加一條沒有執行者的 |

第 1 與第 4 是承重的兩條。它們決定了這一節的形狀:一個**封閉的、宣告式的**工具登錄冊
(`agent/tools.py`),外加一份**從 `agent_node` 自己的 `create_publisher` 導出**的 egress 通道普查。
**MCP 客戶端本身、Client Credentials 憑證流、Strands 殼全部是在機半段**,要網路與一台伺服器。

| ID | 測試項 | 方法 | 通過標準 | 突變體 | 狀態 |

**修正 1(第 1 條缺陷的處理方式,設計上的關鍵決定):**
「MCP 之後工具面不再由 repo 導出」的順手修法是**信任探索**——把伺服器提供的工具併進目錄。
這一節反過來做:`reconcile()` 把「伺服器提供、repo 沒宣告」當成 **finding**,`invoke` 對它回
`UNKNOWN_TOOL`,而 `offered` 是一個**只能縮小**的輸入。代價講明:一個合法的新伺服器工具需要
改一次 `agent/tools.py` 才能用,也就是需要一次 review。這是刻意選的代價,不是遺漏。

**修正 2(第 4 條缺陷:一個狀態變成六個,而不是兩個或五個):**
`REFUSED` 是關於**政策**的主張,`UNREACHABLE` 是關於**網路**的主張,`ERRORED` 是關於**我們自己**的
主張(宣告了工具卻沒有執行體),`NOT_OFFERED` 是關於**伺服器漂移**的主張,`UNKNOWN_TOOL` 是關於
**模型**的主張。Converse 的 `toolResult.status` 只有兩個值,所以 `agent_node` 仍然只送
success/error——但**結果狀態進日誌**,因為「政策拒絕」與「連不上」事後不能長得一樣。
這與 T-C4 的 `ran` 旗標、S7 的 `errored ≠ allowed` 是同一族。

**修正 3(第 5 條缺陷:兩種「沒有執行者」要分開):**
`NOT_WIRED`(執行者在 repo 裡而沒有呼叫者)與 `NO_ENFORCER_TODAY`(沒有東西可以呼叫)是同一個缺席、
差很多的修復成本。把兩者折成一個值會讓 S7 被描述成保護。而 `/speech/say` 那一格的 `NOT_WIRED`
是**導出**的:一份 import 普查。**它被設計成在 S7 的在機半段落地時變紅**——一句散文不會注意到明天。

**修正 4(把兩個閘拴在同一個表上):**
`invoke` 對遠端工具的拒絕理由**讀的是 egress 表**(`EGRESS[MCP_TOOL_CALL].enforcement != ENFORCED`),
不是另寫一條規則。閘與普查於是不可能各說各話,因為只有一份。
對稱地,`MCP_TOOL_CALL` 那一列的 `model_reachable` 由 `REGISTRY` 導出來對帳——
宣告一個可以被導出的值,正是一列開始過期的方式。

**修正 5(這一輪順手拆掉的第二個創造者):**
`skills/loader.py` 原本同時持有 `TOOL_NAME`、`TOOL_CONFIG`、`run_tool` 與 `MAX_TOOL_HOPS`。
搬走它們不是整理:當那個模組持有工具面,「模型能碰到哪些工具」就由**知道技能的模組**回答,
第二個工具會被接在第一個旁邊,而整個工具面會繼續叫一個子系統的名字。
`read_skill_file`(執行體與 T-I3 的路徑柵欄)留在原處。
`MAX_TOOL_HOPS` 一起搬,理由同構:它界的是**每一次**工具跳轉,不只是技能讀檔。

**修正 6(搬家開的洞,由測試補上):**
規格搬走之後,L2 包裝句仍然寫著「需要細節時用 `read_skill_file` 讀」——**散文沒有任何東西在檢查**。
一份指名了沒人宣告的工具的提示,等於每回合都花在一次只能回 `unknown_tool` 的呼叫上。
所以候選名由**組好的提示**用 snake_case 形狀抓出來(今天恰好抓到一個),再要求它是登錄冊的子集;
`"read_skill_file" in prose` 這種寫法**注意不到新名字**,那正是這個 repo 反覆踩到的同一個洞。

**這一節沒有測到什麼,寫在數字旁邊:**
**沒有任何 MCP、任何 OAuth、任何網路。** 今天 `REGISTRY` 宣告零個遠端工具,所以六個結果裡的四個、
效果拒絕、以及 `reconcile` 的兩個方向,全部**靠注入的表**證明可達——那是「分支要可達才算存在」的
唯一辦法,也如實反映系統的現狀:這台機器人今天能做的事,是讀自己的技能檔,沒有別的。
Client Credentials 流(mcp python-sdk v2 的 `ClientCredentialsOAuthProvider`、
OAuth 2.1 的 PKCE 與 RFC 8707 `resource`、RFC 9728 發現)、token 的落盤(`0600`、repo 之外)、
以及憑證**到不了提示區**的證明(要用 T-C5 那個「值落在哪一區由它從哪個參數進來決定」的同一個論證)
都是在機半段。`TOOL_SPEC_CEILING = 400` 今天的實測是 **140**(單一工具,序列化後的字元代理),
而「常駐目錄每回合都收費」目前是 `spec_findings(resident=True)` 的一句 **report,不是閘**——
真正的 per-turn 成本要在機上用 `usage.inputTokens` 量,和 T-I1 同一個校準。

**這一輪學到的四件事,寫在數字旁邊:**

**一、一張會解析的圖仍然可以不能讀。** 第一版草稿的 7 個區塊**全部**解析成功、
**全部**繪出、0 個 error——而 §1 是 3141 px 寬,有一棵決策子樹被畫到「裝著它兄弟節點的
subgraph」外面,還有邊沿著整個畫布高度蛇行。GitHub 的檔案視圖內容欄約 880 px,而縮放
會一起縮標籤:3141 px 下一個 14 px 的標籤大約渲染成 **4 px**。所以「解析成功」不是
oracle,**寬度**才是,而其餘的缺陷是人看 PNG 看出來的。修法不是調參數,是承認**根因是
在一張圖裡混了兩種圖**:程序與 topic 的資料流圖(`architecture.svg` 已經在畫)和一個
回合的決策流,兩者的版面約束互相衝突。改成線性 TD 決策鏈、topic 只當邊標籤、
**標籤是圖說不是解釋**(理由搬到圖下方的散文),最大寬度從 3576 掉到 **1498**。

**二、Mermaid 把沒宣告的 id 畫成一個標著裸 id 的方框,而且不回報任何錯誤。**
第 5 個區塊引用了 `memory`,而那個 id 只在第 4 個區塊宣告過。沒有 parse error、
沒有 warning——它就畫了一個標籤是 `memory` 的框。這是**只有繪出來才看得到、
任何 parse 都不會報**的缺陷,所以它變成 T-M3 的第三條:每個區塊自足。

**三、一個動了的點不等於一個走在它路線上的點,而一個「有閘」的閘不等於一個會開的閘。**
`@keyframes` 巢在 `@supports` 裡面會解析、會列在 `cssRules` 裡、`animation-name` 也算得
出來,但**不會動**(Chrome 141,5.6 秒內 14 個點一個都沒移動)——只有「賦予名字」的那些
規則該放進支援查詢裡。而 offset 變換錨在使用者空間原點,所以一個被動畫的 `circle` 上的
`cx`/`cy` 是**疊加**在路徑點上的(量到 `getBBox` (575,474) 對 `getBoundingClientRect`
(1154,952))。這一段的第三個量測是**推送之後**在 Chrome 151 上做的,而它比前兩個更陰:
`CSS.supports('offset-path', 'path(""))` 在 Chrome 151 是 **false**,而
`path("M 0 0 L 1 1")` 是 **true**。`path("")` 正是每一份特徵偵測範例的寫法——
用它寫的閘會在一個**完全支援**這個特性的瀏覽器上關上,每個點就停在 `opacity: 0`,
圖靜靜地變成靜態圖,而這個檔案裡原本每一條檢查都還是綠的:閘在、巢對、底態在。
所以現在檢查的是**閘的引數**,不只是閘的存在(T-M6 第二條 + `supports_argument_emptied`)。
三條都是純文字檢查,因為離線套件裡沒有瀏覽器。

**四、突變門檻要二分出來,而且要來自被檢查的那個量。** 把每個框放大 14 px,
**沒有任何判決改變**;20 px → 0 個 finding,21 px → 2 個,22 px → 3 個,23 px → 9 個。
所以測試同時斷言**兩半**(20 乾淨、21 必抓),否則一個對任何輸入都開火的檢查也能通過。
而 20 px 這個數字來自 `meta["rects"]` 裡最近的一對框(`disk`/`cloud`),它和瀏覽器那一趟
量到的 11.5 px「文字到框的最小空隙」是**兩個不同的量**,不能互相借用。

**這一節沒有測到什麼,同樣寫在數字旁邊:** 離線套件裡**沒有瀏覽器、沒有 node**,
所以像素是**引用**而不是重新量測——`docs/evidence/mermaid-render.json` 是那一趟真的
Mermaid 11 + Chromium 的記錄,而 T-M5 檢查的是「這份引用自己前後一致」而不是「今天的
渲染器還是這個寬度」。`tallest_edge_frac_of_canvas` 是**記錄,不是閘**:一個共用的
提早退出終點合法地會產生一條貫穿全高的邊(第 8 塊的 `REFUSED` 0.711、第 7 塊的停止轉移
0.712),閘住它會禁止正確的圖,而且**抓不到真正的缺陷**——真正抓到的是寬度。
動畫真的動起來、以及 `prefers-reduced-motion` 真的靜下來,只有在真瀏覽器裡驗過一次
(`docs/evidence/architecture-animation.json`,Chromium 151,T-M9 斷言那份記錄引用的閘
字串真的出現在出貨的 SVG 裡);離線的那一半只斷言「讓它成為可能」的那個 CSS 結構。

而那一趟本身有兩件**沒量到**:第一,`document.timeline.currentTime` 與每一個
`Animation.currentTime` 在等了 3 秒之後都還是 **0**——自動化環境根本不推進動畫時間軸,
所以相隔 2.5 秒的兩張截圖回來是**位元相同**的(md5 `ba1ba56eb748` 兩次都一樣)。
那量到的是 harness 而不是圖:一個凍住的時間軸和一個壞掉的動畫,長得是同兩張截圖。

### N. 休眠接縫普查(`infra/wiring_census.py` 與 `infra/dormant_seams.tsv`)

這一節存在的理由是一個量到的數字:**這個 repo 的五個承諾裡有四個只有 pytest 到得了**。
`agent/context.py:261` 的 `assemble()` 收 `card` 與 `recall`,`agent/agent_node.py:83`

「寫下來的東西彼此一致嗎」,沒有一個問「跑起來的那個行程到得了這裡嗎」。

所以這一節的主張跟前面每一節都不同種類:它不是「某個函式行為正確」,而是
**「這棵樹裡哪些代碼是活的」,而那句話必須會過期**。它的形狀照 §2.M 的 T-M7
(`graph_gaps.tsv`)抄:普查導出事實、TSV 帶具名理由、雙向都查、陳舊列本身是 finding。

**這一節有一個底線是檔案數,而不是接縫數**:`test_the_census_reads_a_useful_number_of_files`
要求普查至少讀到 35 個 `.py`。接縫數**故意沒有底線**——R1 的每一個 PR 都應該讓它變小,
在那裡放一個底線等於因為接線成功而報紅。

**這一節沒有測到什麼:**「到得了」是**呼叫圖上的可達性**,不是訊息真的流過去。
一個模組被 import、被呼叫,不代表它在真機上被走到——那屬於 L4,而 L4 擋在安全群組的
`/32` 上。反方向也要說清楚:普查說一個檔案 unreached,證明的是**這棵樹裡沒有靜態呼叫
路徑**,不是它永遠不會被執行;`importlib` 或字串反射會繞過它,而這棵樹裡今天沒有那種寫法。

**兩個邊界是在合成樹上測的,而那是一句量到的覆蓋率陳述,不是偏好。** 磁碟上兩個
`_` 開頭的 keyword-only 參數(`erase.delete(_after_step=)` 與
`store.Store.__init__(_allow_ephemeral=)`)一個在普查報 unreached 的檔案裡、一個在被
跳過的方法上,所以**這兩條 skip 在真實樹上一次都沒有被走到**。
一條沒有東西走到的邊界,是一條沒有人檢查過的邊界。

**這一節的產物包含兩列 `defect`,而那是寫它的收益。** `safety/guard.py` 的
`gesture_findings()` 與 `spoken_text()` 不只是沒接上:`agent/agent_node.py:265-269`
用自己的 inline regex 把同兩條規則實作了第二遍,而**活著的那一份沒有白名單檢查**。
今天沒有東西不安全地到得了致動器,只因為 `body/body_node.py` 做
`GESTURES.get(name)` 而把不認識的標籤靜默丟掉——一個在下游的、意外的、從不進稽核的
containment,而且那個檔案零測試。`tests/test_wiring_census.py` 把這兩列釘在那兩段
inline regex 與那句 `GESTURES.get(name)` 上,所以這個重複**不能只在一邊被靜默解掉**。

**這一欄是補回來的,而它為什麼曾經被刪掉本身就是要記下來的事。** 前一版把預算欄整欄
拿掉,而一個**被刪掉的**預算跟一個**沒達成的**預算,在文件上長得一模一樣——差別是後者
還會讓下一個人知道要做什麼。所以現在寫的是超標,不是空白。

**2026-08-26 在這台 MacBook 上量到的**(每一支都 `rc 0`,CPython **3.12.12** /
pytest **9.0.3**。這裡把**當天全部的讀數併在一起**,每一支附它自己的 n,
理由在下面三段 —— 分批寫會得到三個互相矛盾的區間,而那正是這一輪的發現):
`pytest -m "not mutation"` = **91.5–120.4 s**(n=4)、
`pytest -m mutation` = **138.6–190.5 s**(n=5)、
整套 `pytest` = **229.0–366.0 s**(n=8)。
1 分鐘 load average 從**無並發負載**到 **8 / 14 核**。
30 s 的預算是計劃書在 1474 個案例之前寫的,今天是 1586 個案例,**超標 3.1–4.0×**。

**這一輪最重要的量測結果不是那些秒數,是「一個窄的 n=2 區間不是穩定性的證據」。**
當天最早兩趟整套讀到 **239.4 與 239.4** —— 到小數第一位都一樣,寬度 **0.0 s**。
同一條指令、同一棵樹、同一台機器,後面六趟讀到
**325.9 / 339.5 / 366.0 / 264.0 / 229.0 / 239.0 s**,八趟合起來的寬度是
**137 s(中點的 ±23%)**。所以那個 0.0 s 量到的是**兩個樣本之間的距離**,
不是這條指令的散佈;而它是這棵樹裡最窄的區間,也是最沒有資訊的一個。
**規則:一個 n=2 的區間只能當下界讀。** L1 與 L3 的區間也一樣 ——
它們的 n 是 4 與 5,不是 20,寬度會再長。

**那 137 s 吃掉了三個我本來要寫下的結論,而先讀寬度就是為了這件事。**
一,**「有負載比較慢」**:寫過一次又拿掉了。四趟有負載的讀數高於 239.4,
但第五趟是 **229.0 s** —— 低於**無負載**的兩趟。所以連方向都分辨不出來,
更不用說我原本算好的「+36–42%」:那個百分比是拿兩個區間的端點相減得到的,
而它在下一趟讀數進來的時候就死了。
二,**「部分之和大於全體」**:兩半相加的範圍是 91.5 + 138.6 = **230.1** 到
120.4 + 190.5 = **310.9**,而整套是 **229.0–366.0** —— 整段都在區間裡面,
所以這一輪**分辨不出符號**,前一輪那個「部分大於全體」既沒被確認也沒被推翻。
`pytest.ini` 記下的快取解釋(分開跑付兩次 Gatekeeper 評估、整套跑只暖一次)
因此仍然只有前一輪那**一次**觀察在支持它。撐得住的規則沒有變:
**不要把三個數字加起來當總時間**;前一輪那句 `90 + 143 = 233 > 205` 也只是一次觀察。
三,**跨輪的水位比較**:前一輪寫的 239.4 落在這一輪的 229.0–366.0 裡面,
所以「這一輪比上一輪慢」這句話也不存在。

**停止規則也要寫下來,因為它是這一段唯一防止自己腐爛的東西。** 我停在 n=8,
而在那之前每加一趟就變寬一次、每一次都殺掉一句剛寫下的結論
(第八趟是六閘的那一趟本身,**239.0 s**,第一次落在區間裡面而沒有把它撐開)。
停止的意思是**這一段的量測窗關了**:窗關了之後為了驗證推送樹又跑過一趟,讀到
**257.0 s**,也落在區間裡面 —— 寫下來但不併進上面的 n,因為一個每次重跑閘就要
改一次的區間永遠關不掉,而**它改不動那個還活著的結論**。下一次併進來的時機是下一輪
重新量的時候,不是下一次跑閘的時候。
我停下來是因為**還活著的那個結論不需要更多讀數**:L1 對 30 s 的超標是
**3.1–4.0×**,而那是一個數量級的差,對 137 s 的散佈完全不敏感。
反過來,任何一個尺度小於 137 s 的計時主張,在這台機器上這種負載下**量不出來**,
而正確的作法是不要寫那句話,不是去跑第八趟。

**直譯器要寫下來,而這一輪剛好有一個理由。** 量測進行到一半的時候,homebrew 把
`/opt/homebrew/bin/python3` 這個 symlink 重指到 **3.14**,而那個直譯器**沒有裝 pytest** ——
於是下一次 `python3 -m pytest` 是 `No module named pytest`,而不是一個紅色的測試。
這棵樹裡每一個閘都是 shell 出去呼叫 `python3`,所以「哪一個直譯器」不是環境細節,
是這些數字與這些 `rc 0` 的一部分:上面的秒數與下面指令區塊裡的每一個閘,全部是在
`/opt/homebrew/opt/python@3.12/libexec/bin` 排在 `PATH` 前面的情況下重跑過的。
一份只寫「在筆電上跑」的文件,沒有辦法區分「套件變慢了」與「`python3` 換人了」。

**這個數字對負載極度敏感,而那件事必須跟數字寫在一起。** 同一支
`pytest -m "not mutation"` 在有並發負載的機器上讀到 **268 s** ——比整套還久,
而 268 s 與當天 L1 最快的 91.5 s 差了 **2.9 倍** ——
也就是說**負載這個座標軸的跨度比整個套件的成長大一個數量級**,
而上面那個 137 s 的散佈就是同一件事在整套上的樣子。
那量到的是機器,不是套件——跟 §1 記下的那件事同一個成因:一個睡覺的替身單獨跑綠,
在整套一起跑的時候把 30 ms 的間隔讀成 **46.0 ms**,而修法是注入時鐘而不是放寬容忍。
所以上面每一個區間都附著它自己的 n 與當天的負載範圍(無並發負載到 load average
8 / 14 核),而**沒有任何測試斷言執行時間**。

**超標的成因是可以指名的,不是「測試變多了」這句廢話:** L3 幾乎全部的時間花在 macOS
對 `~/Downloads` 底下每次 script exec 的 Gatekeeper 評估上(所以同一組測試在同一台機器
上會落在區間而不是點值)。而每一輪新模組的邊際成本是**單獨量過的**,方法是**成對相減**:
這一輪把 `tests/test_doc_status.py` 交錯地拿掉再加回去兩次 ——
**99.2 → 103.0(+3.8)**、**90.2 → 93.9(+3.7)**。

**這一輪學到的是「成對」這兩個字承重,不是那個 +3.8。** 兩對之間的**絕對水位漂了 9.0 s**,
是效應本身的 2.4 倍;把第一對的 103.0 拿去跟第二對的 90.2 相減,會得到 **+12.8 s** ——
一個把機器的漂移全部記到新模組頭上的數字。所以邊際只在**背對背成對**的形式下讀得出來,
而它一旦以「這一輪 91.5 對上上一輪 90」的形式出現,就已經在量機器了。
前一輪對 `tests/test_wiring_census.py` 量到的 **+9.06 s**(81.78 → 90.84)是同一個方法的
一次觀察,而這一輪的兩對(差值穩在 0.1 s 之內,水位卻漂 9 s)正是那個方法為什麼可信的證據。

`tests/test_doc_status.py` 的 37 個案例裡,`-m "not mutation"` 只跑 **13 個** ——
另外 **24 個掛 `mutation`**,落在 L3。所以 L1 的 +3.8 s 是那 13 個的價錢,
而 L3 當時的移動(前一輪 136–143、那一輪 138.6–159.3)**整個落在重測寬度裡面,
量不出來**;要把那 24 個的價錢寫下來,得對 L3 也做一次同樣的成對相減,而那一輪沒做。
一個沒做的量測寫「未量」,不寫一個由兩個區間相減出來的數字。

**這一輪 L3 也「移動」了,而那個移動最後被自己的區間吃掉,這件事值得留著。**
中間兩趟讀到 190.2 與 190.5,對照前面的 138.6–159.3 看起來是一次真的變慢;
第五趟讀到 **153.0 s**,整條 L3 於是變成 **138.6–190.5(n=5)**,而所謂的移動
整個落在裡面。所以這一輪新增的 **4 個**突變案例的邊際成本寫**未量** ——
順帶說明為什麼那個數字本來就不可信:那 4 個是在行程內對一個純模組做文字修補(毫秒級),
不是 L3 那些每次都付 Gatekeeper 評估的 script exec,把 31 s 除到 4 個案例上得到
**7.8 s 一個**,沒有任何機制支撐它。**歸因要靠背對背成對相減,靠兩個區間相減得不到。**
**這是一個已經付掉的、知道價錢的成本**,不是一句「測試變多了」。

**R3 會讓這張表的成員由 marker 導出而不是手寫**,那時 L2 才會有自己的秒數;
在那之前,L2 那一格寫的是「量不出來」,不是一個猜的數字。

L4 的成本要更新:計劃書寫「Track C 合計 < $1」,而實際已經超過。
已跑的部分是 **6 次 M1 呼叫 + 120 次串流呼叫(maxTokens 256)+ 66 次 converse(maxTokens 900)
+ 兩輪 × 3 組 × 32 次 `apply_guardrail`**,其中 effort 那一組跑了**兩次**——
第一次的 M3 用了會釘死長度的 prompt(§2.K 修正 4),那一次的錢是為了發現這件事付的。
按 output token 量級估在 **$1 上下**,不是 < $1;
精確金額要等 Cost Explorer 落帳,而**估算值不該被寫成量測值**。

指令:

```bash
pytest -m "not mutation"     # L1 + L2,每次存檔
pytest                       # 全部,PR 前與推送前
pytest -m mutation           # 只跑 L3
infra/check_deploy.sh        # T-J1 單獨跑,必須印 0 findings
```

L3 為什麼是雙峰的、環境是什麼,見 `pytest.ini` 的 `mutation` marker 說明(跟 marker
同一個檔案,所以它不會跟代碼脫節)。那裡寫的是**區間不是點值**:L3 幾乎全部的時間花在
macOS 對 `~/Downloads` 下每次 script exec 的 Gatekeeper 評估上,而那個評估有快取,
所以「部分之和大於全體」在這裡是正常的,不是量錯。
兩組數字的**分母不同,不能互相取代**,所以兩組都留著:上面那一欄的
91.5–120.4 s / 138.6–190.5 s 是 2026-08-26 對**整個層**(1586 個案例、其中 333 個
突變體)跨當天全部讀數的量測;`pytest.ini` 裡 2026-08-22 那組是對**一個子集**(145 個案例、
其中 18 個突變體)的量測,它存在的目的是展示雙峰與快取效應,不是報告這一層要跑多久。
把後者當成前者,會得出「L3 只要 60 秒」這個今天差了 **2.2–3.2 倍**的結論。
`pytest.ini` 裡那兩個整層的數字(案例數與突變體數)從這一輪起由 `infra/doc_counts.py`
閘住 —— 在那之前它們停在 1512 與 304,而它們就坐在一段「為什麼每一輪都要重新量」的
散文裡。**一段解釋數字會腐爛的散文,本身就是最容易腐爛的地方**;`DOCS` 的成員資格因此
是「引用了這些數字的檔案」,不是「`docs/` 底下的檔案」。

**沒有任何測試斷言執行時間。** 跑得慢是筆電慢,不是失敗——一個會因為機器忙而變紅的
測試,兩天內就會被加上 skip。

## 4. 人工 UAT 檢查表(不可自動化的部分,逐項簽核)

1. 冷啟動第一句**聽得到**身分揭露(不是只在畫面上)。

5. 一局猜拳:節拍不飄;說「停」立刻停;冷卻期內不重開。
6. 連玩 20 局:**它有沒有變得不好玩?**——這是 H 級 oracle,只有人能判。
   若「總是贏」不好玩,要調的是 HRI 預設值,不是演算法。
7. 講長故事 → 中途插話 → ≤0.5 s 閉嘴並回應新話題。

## 5. 已知盲點(誠實邊界)

- **多模態切分閾值沒有任何已驗證先例。**現有的人類對齊證據全在文字 token 串流上,
  所以 T-B3 的 0.80 是我們自己選的回歸線,不是驗證過的標準。
- **「遺忘讓記憶更好」沒有任何論文做過 decay vs no-decay 的 ablation** →
  T-F6 只能比出我們自己的偏好,不能宣稱一般結論。
- **粵語護欄有效性零量化數字** → T-G4 的粵語部分只能證明「這 10 條被擋住」。
- **T-D5 的 n=60 CI 很寬**,只夠偵測大效應(文獻效應量 27–86%,夠大);小改善測不出來。
- **紅隊與注入測試永遠是單邊的**(規則 3)。安全的證據強度上限就在這裡,
  這也是為什麼硬邊界要放在 schema 而不是文字過濾。
- **T-J1 只看 `run_ec2.sh` 這一條部署路徑。**`provision.sh` 產生的 `ssh_config`/`local.env`
  沒有對應的守衛,因為它們是帳號專屬且 git-ignored,無法在 CI 裡驗。
- **entrypoint 掃描排除 `tests/`。**這不是豁免:tests 不進部署,而「有測試檔沒人跑」
  這個相同形狀的缺陷由 T-J2 的逐模組收集下限接手。兩個檢查合起來沒有縫。
- **§2.H 的四個對手全是我寫的腳本,裡面沒有人。**它們界定的是模擬雜訊
  (n=100 seeds),不是「這些對手能不能代表一個人」。特別是 T-H2 ④ 的 +0.0931
  是機器對腳本;真人會用機器所沒有的方式適應(例如乾脆停止思考、改成真隨機)。
- **T-H6 的結構閘證明的是原始碼形狀,不是執行期行為。**它能保證節拍路徑上沒有一行去問模型,
  但保證不了 `_arm` 本身在真機上夠快;那件事只有 `arm-cost.json` 這種量測能講,
  而它是在**筆電**上量的(EC2 上的 T4 主機沒有重量過)。同樣地,呼叫圖是對 `self.opponent`
  這個名字導出的:一個把模型藏在別的屬性名後面的重構會讓這個閘看不見——
  這正是為什麼 `test_model_touchpoints_are_exactly_the_four_named_methods` 要把
  **觸碰者的名單本身**也釘住,新增一個觸碰點就要紅。
- **T-H4 沒有裁決權,而且方向是誤導的。**order-1 在我們的 fixture 上領先,
  但那些 fixture 就是 order-1 過程,所以那個領先是同義反覆。order 集合要動,
  得先有真人資料;在合成 fixture 上調 order 等於在自己的假設上過擬合。
- **「一局一分是否等於文獻裡的 a = 2」仍未查證**($0,讀原文即可)。
  Track B 已設計成不依賴 `gcr = g0 + (a−2)(1/6 − τcr/2)`——那個式子在 a = 2 時
  優勢恆為 0,所以我們靠實測 + 閘,不靠它。這也是 §2.H 修正 1 的另一面:
  均勻對手上的分數在原理上就沒有訊號,能當閘的只有 Ville 界。
